## Hard rule

Only add, edit or remove comments (and the docstrings the language file allows: Python docstrings, Elixir `@moduledoc` / `@doc` / `@typedoc` strings, Clojure docstrings in `def` forms), plus blank lines next to comments where the comment style or the language file needs them (never elsewhere, and never to move code). No reformatting, renaming, reordering, re-quoting, or changes to string literals, templates or markup. Every other string is code, even one that tools publish as documentation (Erlang `-doc`, Clojure `:doc` metadata, schema `description` strings): never edit it, and put a wrong one in the bug report. If keeping a line unchanged forces an awkward comment placement (for example, a callback inline in an expression), put a comment above the statement rather than splitting the line.

- A shebang (`#!…`) and anything a language requires on the first lines (magic or encoding comments, `<?php`, `package`, directive prologues) stay where they are. Put the file header after them, or where the language file says.
- Never put a comment inside a string, a template, a heredoc, a JSX text run or markup: there it is content, not a comment. Never add markup comments (`<!-- -->`, `{# #}`, `<%# %>`).
- **Locked regions.** Where the grammar cannot parse the code (newer syntax than the bundled grammar knows), the checker compares the smallest enclosing declaration byte for byte, or, when the error sits directly in a body (a namespace, class or statement list), the broken statement, its nearest code neighbours and the comments between them (only the statement when the grammar merely inserted a missing `;`). Leave comments inside a locked region exactly as they are. When the lock is a whole declaration, its own leading doc comment is outside the region and may still be written; when the lock is a statement in a body, the comments between it and its neighbours are inside it. The `LOCKED:` lines of the frozen scan name the files and the line ranges of their regions; the language files name the syntax that causes them, and this rule decides the region's size everywhere.
- Doc comment indentation always matches the code it documents. Never re-indent code to match a style.

## Failure protocol

- When the checker reports `CODE CHANGED`, `LAYOUT CHANGED` or `FROZEN COMMENT CHANGED`, a syntax check fails, or (in the main session's final verification) a test count moves, the cause is the edit. Restore that file from `<scratchpad>/orig/`, then redo only its comments. A test count does not name a file: the main session first finds the group by restoring one group's files at a time in its work copy, then applies this protocol to that group's files.
- **Never edit code, tests, configs or the checker to make a check pass.** If you believe the checker is wrong, stop and report it with the exact output.
- If the same file fails twice, leave it restored to the original and list it in your report as not documented, with the reason. The main session adds each such file to `<scratchpad>/restored.txt`.

## Universal rules (every language)

- **Coverage:**
  - **Precedence.** Where a language file differs from these universal rules (it removes an exemption, adds one, or requires more members), the language file wins, and the coverage scan enforces the language file's version.
  - Passing the coverage scan is necessary, not sufficient: rules it cannot check (closures, callbacks, effect bodies, inline types, event handlers) are checked by reading.
  - A file header on every file, in the form the language file gives: a summary, then the file's role (what it exports, registers, mounts or renders; which routes, events, jobs, commands or types it defines). Where the language file says one type per file is the convention (Java, C#, Kotlin, Swift, a Ruby class file), that type's doc comment is the header.
  - A doc comment on every type (class, interface, trait, protocol, struct, enum, union, record, type alias, module or namespace), on its members (fields and properties; enum values and variants only where their meaning isn't plain), and on every function, method, constructor, getter and macro, in the language's doc comment form.
  - Exemptions that apply where the language's coverage scan implements them (the language file lists its exact forms; where a language file does not list one, it does not apply): a constructor (or field) that only receives injected dependencies; an override or trait / interface implementation that inherits its docs; the implementation after documented overload signatures; a setter whose getter is documented; test functions and test callbacks in test files; include guards and generated code. The language file lists the exact forms.
  - Every statement that registers a handler with a body (routes, middleware, event and message listeners, hooks, jobs, commands, signals, scheduled tasks) gets a doc comment directly before it.
  - Optional: private module-level constants and configured instances get a one-line comment when the name does not say what the value is for.
- **Content:**
  - A summary sentence ending in a period, in the voice the language file sets. Separate a file header from the first statement with one blank line.
  - A longer description when behavior isn't trivial: side effects; database reads and writes (which tables, collections or models); transactions and locking; cache reads, writes and invalidation; HTTP calls to other services; jobs enqueued; events emitted; files written; environment variables read; auth and permission requirements; error paths (what is thrown, returned or which status is sent); concurrency (threads, tasks, goroutines, locks, cancellation); idempotency and retry behavior; where the code runs (server, client, worker, ISR).
  - Every parameter, and the return value, in the language's form. Never repeat a type the signature already states, unless the language file says the dialect requires it.
  - Every error the function raises, throws, returns or panics with on purpose, and failures the caller must handle.
  - `@since` (or the language's version tag) only under the `@since` policy in the rules file. Never invent a version.
- **Routes and handlers:** name the method and path (`GET /api/notes/:id`), what authenticates and authorizes it, the inputs it reads (params, query, body, headers, cookies) and how they are validated, each response status and body it sends, and the errors it passes on. Use the route map in the rules file for routes registered elsewhere (prefixes, mounted routers, file-system or annotation routes). A route registration's comment describes the route; parameters such as `req` / `res` need tags only on handlers defined on their own.
- **Events and messages:** follow the event map in the rules file. The full doc comment (what it means, when it fires, its payload shape) goes only at the chosen emitter; every other emitter and every listener gets one line: `Listens for 'note:created' (documented in src/notes/service.ts).`
- **Shared shapes:** follow the shapes list in the rules file, which names each shape's file and exact type name. Describe each shared type (request / response bodies, records, store state, config objects, payloads) once there, and reference it by name elsewhere. Never copy a shape into a second definition, and never add an alias for a type that already exists.
  - A shape that is not on the list: if only your files use it, define it once in the file that builds it. If files outside your group use it, describe it in prose where you need it and name it in your report. Between waves the main session adds it, with an owner file and type name, to the shapes map, so the next wave's rules files list it.
- **Environment variables:** follow the env map in the rules file, which names the exact `file:line` for each variable. Document each variable once there (meaning, required or optional, default, server-only or exposed to clients). Never write a real value, a secret, or anything from an `.env` or credentials file into a comment.
- **Preserve.** The checker enforces these classes; the language file lists their members.
  - **Frozen** (never add, remove, move or edit; the whole comment stays byte for byte, in the same place): lint, type-check, formatter, coverage and compiler directives; build and code-generation markers; comments that a tool executes or turns into code (doctests, example output, cgo preambles, spec-generating blocks); i18n extraction comments; license, copyright and credit text; `@generated` markers.
  - A directive that applies to the next line or node must stay the **last** comment before its code: put any new comment above it, never between it and its line. A trailing directive stays on the code's line, after the code.
  - **Frozen tag lines** (one line each, never added, removed or edited): tags that change what tools emit or check, such as `@deprecated`, `@internal` and test-runner pragmas. A deprecation is a claim only the authors make.
  - **Kept** (keep the existing line; you may add new ones): `@see`, `@link`, `@author`, `@since` under its policy, and, when the rules file says types are checked, the type and name on typed tag lines (`@param {Note} note`, `@param int $id`): never loosen or change such a type; report a wrong one as a bug. You may add a type to an untyped tag.
  - **Trigger words.** Directives are recognized at the start of a comment or comment line. Never start a new comment, or a line inside one, with a directive word or a license word (`Copyright`, `©`, `(c)` followed by a digit, `SPDX-License-Identifier`, `Licensed under the`, `Permission is hereby granted`, `For the full copyright and license information`), and never name the GNU (Lesser, Affero) General Public License anywhere in a new line. The checker would treat it as frozen and fail it. Reword (`The footer shows the copyright banner.`).
- **Comments a tool reads as content.** When the rules file says a tool turns comments into published text (OpenAPI generators, schema descriptions, CLI help, API docs sites, component docs), the summary written on those declarations becomes that text. Write it for the reader of that output: no internal notes, no bug remarks, no file paths.
- **Inline comments:**
  - They explain **why**, not what: security reasons (auth checks, input validation, escaping, SSRF or path-traversal guards, CSRF), race conditions and ordering constraints, edge cases, retries and backoff, caching, back-compat shims and fallbacks.
  - Don't narrate trivial lines.
  - Describe only what the code actually does. Never invent behavior. If unsure, read the caller or the callee.
  - A comment may state a fact a reader needs ("The body is not validated here."), but never a verdict, a fix or a `TODO`. Bugs go in the report.
