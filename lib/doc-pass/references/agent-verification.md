## Agent verification

Each agent checks only its own files.

Before editing, read your `agent-<n>/frozen.txt` (with no agents, `<scratchpad>/frozen.txt`). Every `FROZEN:` line names a comment or tag line that stays byte for byte, in the same place. A `LOCKED:` line names a file with regions compared byte for byte (see **Locked regions**).

Files with invisible or escaped characters (`\uFEFF` and other Unicode escapes in strings or regexes, literal BOM, zero-width or bidi characters, tabs inside string literals): the Write and Edit tools can turn an escape into the literal character, or drop one. Insert comments in these files with a small script in your agent folder that reads and writes bytes, and check the file with verify before editing the next one.

After editing, run:

- The verify command from the rules file, on its own files, with the flags the rules file gives (`--schema-tags`, `--checked-types`, `--line-limit`). It is also the syntax check: a JS / TS file that no longer parses is reported as `CODE CHANGED: <file>: parse error …` (in a component: `CODE CHANGED: <file>: <script> block N: parse error …`), and a tree-sitter file that gains a parse error changes its code stream. If another agent is editing in parallel, look only at your own files in the output.
- The language's own syntax check when the rules file lists one, not one marked `not available:` (`node --check` for plain `.js` / `.mjs` / `.cjs` without JSX, `php -l`, `python -c "import ast, sys; ast.parse(open(sys.argv[1]).read())" <file>`, `ruby -c`, `gofmt -l`). Never run `node --check` on JSX, TypeScript or components. Skip the syntax check for a file that already failed it before any edit: those listed in `baseline/syntax-fail.txt` (the rules file names them), and `READ BY HAND` files. The verify parse covers them. Never run a tool that writes into the project (`python -m py_compile` writes `__pycache__/`; `cargo`, `dotnet build`, `mix compile`, Gradle, `swift build` and `cabal build` write build folders, and so do `make`, `cmake --build`, `erlc`, `rebar3` and `dart analyze` / `flutter analyze`): the main session runs those in its work copy between waves.
- The coverage command from the rules file, on its own files, with `--context-from` (and `--line-docs` for files listed in `line-docs.txt`) as the rules file gives it: it must print `OK` (no `MISSING` or `UNPARSABLE` lines). A `LOCKED DOC` line is a declaration whose doc slot is inside a locked region (it starts inside one, or it shares one with the broken statement before it): leave it, and list it in your report. A `READ BY HAND` line is a JS / TS file Babel cannot parse: coverage cannot scan it, so check its docs by reading and list it in your report. A declaration locked on its own still gets its doc comment above it; coverage reports that one as `MISSING DOCBLOCK`.
- No comment line you wrote exceeds the project's line limit (from `.editorconfig` `max_line_length`, or the formatter or linter config; else 100): verify reports `LONG COMMENT LINE` for each one. Existing code lines over the limit don't count (nor a trailing comment on one), nor do comment lines kept unchanged from the original (a long URL in a block you added a summary to).
- **Where to run linters and formatters:** in the work copy, never in the project (they write caches such as `.ruff_cache/` and `.mypy_cache/`, and the project may have no dependencies installed). First copy your edited files there: `rsync -a --files-from=<agent folder>/files.txt <project>/ <scratchpad>/work/`, then run each tool from `<scratchpad>/work/` on the same relative paths.
- Formatters in check mode, when the rules file lists them (`prettier --check`, `gofmt -l`, `cargo fmt --check`, `ruff format --check` / `black --check`, `pint --test`, `rubocop`, `dotnet format --verify-no-changes`, `clang-format --dry-run -Werror`): every file that passed before must still pass. Formatters re-indent and re-wrap comments, so a failure means a comment's indentation or wrapping is wrong: fix the comment, never run the formatter in write mode.
- Linters the rules file lists that run per file, on its own files, compared with the baseline per file and rule: **no new** counts; documentation rules (`jsdoc/*`, pydocstyle / ruff `D`, `Style/Documentation`, `missing_docs`, CS1591) should go down.
- Do not run the test suites or module-wide checks (`go vet ./...`, `staticcheck ./...`, `golangci-lint run`, `cargo clippy`, `cargo check`, `cargo doc`, Gradle / Maven builds): they are slow, lock shared caches and share databases with other agents. The main session runs them once per wave.

Follow the **Failure protocol** on any failure. Write your report to `report.md` in your agent folder, with these sections: **Files** (done, and left undocumented with the reason), **Verification** (each check and its result), **Shapes** (shapes described in prose that belong on the shapes list, each with the files that use it), and **Bugs** (bugs and code smells you noticed, each with `file:line`, a one-line problem and a one-line fix; never fix them). Then reply with one line only: files done, files left undocumented, verification result. If the Write tool refuses `report.md`, reply with the full report instead.
