## Discovery details

Step 1 of `SKILL.md` points here. Every output that grows with the project (search results, the file walk, the frozen scan, the maps) goes to a file under `<scratchpad>`, never into the conversation whole: read such files with `grep -c`, `grep` for one package, or in chunks.

### Files

- **The walk.** `node <scratchpad>/checker/verify.mjs <project> --list-files --list-skipped > <scratchpad>/walk.txt` lists every file with an extension from the language table, one relative path per line, then a `SKIPPED: <file>` line for each source file left out as binary or marked generated, and a `SKIPPED DIR: <dir>/` line for each pruned folder named like build output (`build`, `dist`, `out`, `target`, `coverage`, `obj`, `vendor`, `__generated__`) that holds source files. Build the list with `grep -v '^SKIPPED' <scratchpad>/walk.txt > <scratchpad>/files.txt`, and show the `SKIPPED:` files and `SKIPPED DIR:` folders in the plan (a prose comment that says "DO NOT EDIT" can hide a real source file, and `internal/build/` can be a real Go package). For a `SKIPPED DIR:` folder that is real source, add its files with `node <scratchpad>/checker/verify.mjs <project>/<dir> --list-files | sed 's|^|<dir>/|' >> <scratchpad>/files.txt`.
- **What the walk skips:** symlinks, dot folders, dependency and build folders (`node_modules/`, `bower_components/`, `jspm_packages/`, `vendor/`, `build/`, `dist/`, `out/`, `coverage/`, `storybook-static/`, `__generated__/`, `target/`, `obj/`, `__pycache__/`, `venv/`, `site-packages/`, `Pods/`, `DerivedData/`, `cmake-build-*/`, Laravel `bootstrap/cache/` and `storage/framework/`), minified and bundled files, `Kconfig*`, IDE helper stubs (`_ide_helper*.php`, `.phpstorm.meta.php`), known generated declarations (`next-env.d.ts`, `auto-imports.d.ts`, `components.d.ts`, `typed-router.d.ts`, `worker-configuration.d.ts`), Vite `*.timestamp-*.mjs`, and files that hold a NUL byte or carry a generated marker in a comment in their first 20 lines (`@generated`, `Code generated … DO NOT EDIT`, `<auto-generated>`, `This file was automatically generated`, `Do not edit by hand`, `Generated by Django`, `DO NOT MODIFY BY HAND` …; `checker-spec.md` has the exact rule).
- **What to remove by hand** from `files.txt`, because the walk cannot know it:
  - the scope choices from intake (tests, scripts, client code);
  - generated clients without a marker (protobuf, OpenAPI, GraphQL);
  - files claimed by the wrong language: `.inc` files that are not PHP (C / C++ includes in zephyr or LLVM have no `<?php`) and `.t` files that are not Perl tests. The checker would parse them as PHP or Perl and fail every edit;
  - the out-of-scope folders and file patterns each language file lists (C# `bin/`, `*.Designer.cs`, `*.g.cs`; Ruby binstubs and `db/schema.rb`; Qt `moc_*.cpp`; protobuf `*.pb.h`; `phpstan-baseline.php`; SwiftGen output; Gradle `.kts` unless the plan lists them; Authenticode-signed PowerShell files). `bin/` itself stays in scope: Dart, Node and Perl CLIs live there;
  - **bundled third-party code** (a copied library, a vendored SDK, a file with its own license header and package name): leave it out by default and list it in the plan;
  - **stale copies** (`*.backup.*`, `*.bak`, `*.old.*`, `*.orig`, `* copy.*`, config variants that nothing loads): list them in the plan and leave them out unless the user brings them in.
- **Never open** secret files (`.env*`, credentials, keys); `.env.example` may be read. Templates and markup (`.blade.php`, Twig, ERB, Jinja / Django templates, `.ejs`, Razor, HTML, CSS, JSON, YAML) are out of scope: read them for facts only.

### Parse check and frozen scan

- `frozen.txt` holds one `FROZEN: <file>:<line> <text>` line per frozen comment or tag line, one line starting `LOCKED: <file>: <n> region(s)` per file with regions its grammar cannot parse (ending with their line ranges, `: lines 12-30, 45`), and a `CODE CHANGED: <file>: original parse error …` line per file that cannot be proven safe at all.
- Read only the failures: `grep -E '^(CODE|LAYOUT|FROZEN COMMENT) CHANGED' <scratchpad>/frozen.txt`. Remove each file whose `CODE CHANGED` line says `original` (`original parse error …`, or `original <script> block N: parse error …` for a component) from `files.txt` and list it in the report. (A plain JS / TS file Babel cannot parse falls back to tree-sitter and stays in scope. Its broken regions show as `LOCKED:` when tree-sitter finds any, and coverage lists it as `READ BY HAND`. It is reported as `original parse error` only when tree-sitter fails too.) Any other failure in this self-compare means the checker is not deterministic on that file: stop before any edit, and fix or report the checker.
- Count the rest per package or top-level directory, for example `grep '^LOCKED:' <scratchpad>/frozen.txt | cut -d' ' -f2 | cut -d/ -f1 | sort | uniq -c`. The plan and the rules show counts; the lines themselves reach agents only as their own slice (step 3).

### Configs, checked types and comment-reading tools

- **Configs and style.** Read each language's lint, format and type-check configs (the language file names them) and the README for the project's own vocabulary. Pick each language's doc dialect as its file says. Note the comment line limit (`.editorconfig` `max_line_length`, the formatter or linter config; else 100). When the project is a package inside a larger repo, these configs can sit in parent folders up to the repo root; read those too, and pass them to the tools in `<scratchpad>/work/` with each tool's config flag (`luacheck --config`, `eslint -c`), since the work copy has no parent folders. With none found, use the defaults and say so in the plan.
- **Checked types.** When doc comment types are checked by a tool (JS with `checkJs` or `// @ts-check`; PHP with PHPStan or Psalm configured), the project has **checked types**: pass `--checked-types` to every verify and selftest run.
- **Comment-reading tools.** If a tool turns comments into published or executed text (JS: tsoa, typescript-json-schema / ts-json-schema-generator / typia, NestJS Swagger `introspectComments`, TypeDoc, Storybook; Python: graphene / strawberry, Click / Typer, FastAPI; Rust: clap; C#: Swashbuckle XML comments; Go: swaggo), note it. For the JS schema generators, **schema tags are on**: pass `--schema-tags`. For the others, ask the user once whether new summaries may flow into that output (recommend yes), and record the answer for the rules.

### Facts library (optional)

When the user points to a folder of framework fact cards (Markdown files, usually one per language or framework, each card with **Trap**, **Reality**, **Detect**, **Fix** and **Source** entries), list the files that match the project's languages and frameworks. Agents read them so a comment states the **Reality**, never the **Trap** (for example, that Ring's `wrap-session` keeps sessions in memory unless a store is set), and use the **Detect** lines to spot bugs for the report. Comments never cite card IDs or copy card text.

### `@since` policy

- Omit version tags unless the project already uses them.
- If it does: keep existing values, and date new symbols from git tags (`git log -S '<name>' --reverse --format=%H -- <file>`, then `git tag --contains <commit> --sort=v:refname | head -1`) or from a changelog entry that names the symbol. Otherwise ask once whether to use the current version or omit it.
- Never change an existing value; list odd ones in the report.
- `git log -S` is slow on long histories: when many symbols need dating, first try a file's first commit (`git log --diff-filter=A --format=%H -- <file>`) and use `-S` only for symbols added later than their file.
- Pass `--since` to coverage only when every existing declaration already carries a version tag and every new one gets one: it flags every documented declaration without `@since`, old ones included. With partial use, check new tags by reading. It checks `@since` on top-level JS / TS declarations and on every PHP, Java and Kotlin declaration that needs a doc comment; check other languages' version tags by reading.

### Maps and shapes

Write each map to its own file: `<scratchpad>/maps/routes.md`, `events.md`, `env.md` and `shapes.md`. **Every row is one line and names every file it involves by its path relative to the project** (`file:line` where a line is meant), so `grep -F -f agent-<n>/files.txt` pulls out the rows an agent needs.

- **Route map.** Write the registration search to a file and read it in chunks; never truncate it (no `head`). List every registration call, including legacy, versioned and static-file routes. For every server route: method, full path (prefixes, mounted routers, file-system and annotation routes resolved), handler `file:line`, middleware / guards / filters, the views rendered with their variables, and the client files that call it. For client routing: each path with its component, guards and the data it loads.
- **Event map.** Every emitted event, signal, socket message, queue job, scheduled task and pub/sub topic by name, with its emitters and listeners. Pick one file per name for the full doc comment and mark it.
- **Env map.** Every environment variable or setting read (`process.env`, `getenv`, `os.environ`, `env()` / `config()`, `ENV[]`, `std::env::var`, `os.Getenv`, options classes, framework runtime config), the exact `file:line` where it is read or validated, and whether it reaches a client. Include any prefix the loader adds (`env.Options{Prefix: "SPIRIT_"}`, Spring `@ConfigurationProperties(prefix)`, Nuxt `NUXT_`), so the documented name is the one an operator sets. That `file:line` is the one place it is documented.
- **Shared shapes.** The types used in more than one file. When a shape already exists as a class, interface, struct, model or typedef, name it; agents reference it and never alias it. Otherwise pick one owner file per shape for its definition **and its exact type name**, so agents in other groups can reference it before it exists. List input shapes separately from stored rows when they differ. Include the objects a factory or constructor function returns when other files use them (`createLogger()` returning `{error, warn, info}`, a job handle with `start` / `stop`): they have no declared type, so they are easy to miss. Shapes found between waves are added as rows, each naming its owner file.

### Groups

- Split the in-scope files into disjoint groups by package, then directory, balanced by line count: 500–900 lines each, never more than about 1,500, and one language per group where practical.
- Keep together, where the size allows: a route file and the service it mainly calls; a Go package directory; a C / C++ header and its source file. (Coverage takes `--context-from` so a split pair does not report false gaps, but the doc owner is easier to see in one group.)
- Under about 900 lines in total, do the work in the main session with no agents.
- More than 7 groups run in **waves** of at most 7 agents.
- When the scope is over about 20,000 lines, show the per-package line counts and ask the user once to choose the packages for this pass, or to confirm the number of waves.

### Baselines

Run every tool with the project's own installed version, in `<scratchpad>/work/`: `npx --no-install …`, `vendor/bin/…`, the virtualenv's binaries, `bundle exec …`, `go vet`, `cargo clippy`. Formatter check modes: `prettier --check`, `gofmt -l`, `cargo fmt --check`, `ruff format --check`, `pint --test`, `rubocop`, `dotnet format --verify-no-changes`, `clang-format --dry-run`. The language files give the full list per language.

### Report ranking

Lead with security (missing authn / authz, injection in SQL / NoSQL / shell / paths / templates, XSS, SSRF, CSRF gaps, secrets reaching clients, unsafe uploads or archive extraction, memory safety in C / C++ and `unsafe` Rust), then data integrity and concurrency (races, missing transactions, unhandled errors, leaked resources), then deprecated APIs for the declared versions.

### The plan
