# Section 1: read the theme

Read this in full before reading the theme. If you split the reading across subagents, give each one this file, `checks.md`, and the return format below.

Read every file in the theme, in full, before you test anything. Reading only the files a grep hits is not enough: bugs hide in files no search points at.

- **Manifest first.** List every file in the theme directory with `find <theme-dir> -type f` into `<work>/manifest.md`. Mark each one as it is read. Nothing is read partially: a file is read from its first line to its last, in as many chunks as it takes.
- **What counts as a theme file:** every PHP file and template, JavaScript, CSS and its source (Sass, PostCSS, Tailwind config), `theme.json`, `style.css`, `readme.txt`, `package.json`, `composer.json`, build configs, ACF JSON, language templates (`.pot`), and any other text file the theme ships.
- **The only exclusions:** editor, agent, and version-control folders (`.git/`, `.remember/`, `.claude/`, `.idea/`, `.vscode/`, and similar tool folders that aren't shipped with the theme), `audit/` (this audit's own output), folders the theme marks as not shipped (listed in `.distignore` or as `export-ignore` in `.gitattributes`; read them only if the theme's shipped code loads them), `vendor/`, `node_modules/`, bundled third-party frameworks and libraries (Redux, TGMPA, Kirki, a copied-in jQuery plugin), minified or compiled files that have a source file in the theme, the media folders `scripts/media-dirs.sh` finds (never read file by file; list each with its size), images, fonts, and `.po`/`.mo` binaries. List every excluded path and why in the manifest. Read the theme's own config calls into excluded frameworks. A minified or compiled file with no source in the theme is read like any other file. Before excluding a bundled library file, check its last 50 lines, and compare its size with the upstream release if its version is known: themes often append their own code to a library file, and that code must be read.
- **Large themes:** for themes over about 100 files, split the manifest across subagents, grouping files that work together (a feature's PHP, JS, and templates in one batch). Each reads its files in full and returns findings, never file contents, in exactly this format so results merge cleanly: `## Files read` (one path per line); `## Data model rows`, `## Inventory rows`, and `## Template rows`, each a markdown table with the columns given below; and `## Candidate bugs`, one block per bug with `- **Check:** <check ID from section 2>`, `- **Where:** file:line`, `- **What breaks:**`, `- **Evidence:**` (the lines of code, quoted briefly), and `- **Confidence:** likely | possible`. Give each subagent the section 1 questions, the section 2 checklist, and this format. If you can't run subagents, read in batches and add each batch's rows and findings to a scratch file outside the theme as you go, so earlier findings aren't lost.
- **Done means done:** don't start section 3 until every file in the manifest is marked read or excluded. Also grep the whole theme for the calls listed below, as a cross-check that nothing was missed while reading.

While reading, answer these questions from the code.

**Content**
- Which post formats does it declare (`add_theme_support( 'post-formats' )`), and what does each format's template actually read to render?
- Which custom post types and taxonomies does it register? Record each post type's `supports` list and taxonomies, and each taxonomy's post types and whether it's hierarchical.
- How does it find images: featured image, attachments with `post_parent` and `menu_order`, `[gallery ids=""]`, or ACF fields? Which image sizes does it register, and what aspect ratio does each image slot show (`add_image_size`, CSS aspect-ratio classes)?
- How does it handle video and audio: an oEmbed URL in the content, a meta field, or a direct file? Which hosts does it parse (YouTube, Vimeo, .mp4)?
- What do sidebars, rails, archives, and the home page show: recent posts, tag clouds, category counts, comment counts, authors, vote or view counters, sort modes that depend on dates or meta?
- Does it display comments, and on which post types? Look for `comments_template()` calls, filters that force comments closed or empty, and any Customizer or theme options switch that turns comments on or off.
- Which values does it compute itself from content (reading time, ranks, term and comment counts, derived caches), and which counters do visitors drive (views, likes, votes, ratings)? For each, find the code that writes it.

**Fields**
- Which post, term, and user meta does it read (`get_post_meta`, `get_post_custom`, `get_metadata`, `get_field`), and what shape does each expect (URL, number, ID list, JSON)?
- List every meta box and custom field. Search for `add_meta_box` callbacks and their `save_post` handlers (the sanitize call shows the stored format), `register_post_meta` and `register_meta`, and field frameworks: ACF (`acf_add_local_field_group`, `acf-json/`), CMB2, Meta Box, and Carbon Fields.
- List every category, tag, and custom taxonomy field: the add-form and edit-form hooks (`{$taxonomy}_add_form_fields`, `{$taxonomy}_edit_form_fields`), their save hooks (`created_{$taxonomy}`, `edited_{$taxonomy}`, `create_term`, `edit_term`, `saved_term`), `register_term_meta`, list-table columns (`manage_edit-{$taxonomy}_columns`, `manage_{$taxonomy}_custom_column`), any media uploader or colour picker script on those screens, and the options some older themes use for term data instead of term meta (`get_option( 'category_' . $term_id )`, `taxonomy_<id>` options).
- List the other field screens the same way: user profile fields (`show_user_profile`, `edit_user_profile`, `personal_options_update`, `edit_user_profile_update`), attachment fields (`attachment_fields_to_edit`, `attachment_fields_to_save`), and quick edit or bulk edit fields (`quick_edit_custom_box`, `bulk_edit_custom_box`).
- List every Customizer setting. Search for `customize_register` callbacks and each `add_setting` / `add_control` pair, Kirki or any other Customizer framework, and every `get_theme_mod()` and `get_option()` call in the templates (some themes read mods that have no control). Also cover the core site identity settings the theme uses: site title, tagline, `custom_logo`, site icon, header image, background, and the homepage settings `show_on_front`, `page_on_front`, and `page_for_posts`.
- For the Customizer, also record each panel, section, and control (with custom control classes and their JS), every `active_callback`, each setting's `transport`, the preview script (`customize_preview_init`) and which settings it binds to, every selective refresh partial (`selective_refresh->add_partial`) with its selector and `render_callback`, and the controls script (`customize_controls_enqueue_scripts`).
- If the theme has its own options or settings panel, list every field in it. Search for `add_theme_page`, `add_menu_page`, `add_submenu_page`, `register_setting`, `add_settings_field`, options frameworks (Redux, OptionTree, Codestar/CSF, Kirki panels, ACF options pages via `acf_add_options_page` and `get_field( 'x', 'option' )`, Carbon Fields `theme_options`, CMB2 options pages, Titan), and every template call that reads those options, such as `get_option( '<theme>_options' )['footer_text']` or a helper like `<theme>_get_option()`.
- For the options panel, also record each page's capability, its `register_setting` option group and whether the form posts that same group, its tabs and how each tab saves, any reset-to-defaults, import, or export tool, the media uploader, colour picker, or other scripts on the page, how errors are shown (`add_settings_error`, `settings_errors()`), and what happens to the options when the theme is switched or deleted.

**Site**
- Which nav menu locations, widget areas, and page templates does it register, and which of them does a template actually display? Are any templates chosen by slug (`page-<slug>.php`, `is_page( 'slug' )`)? Does it add fields to menu items (a custom `Walker_Nav_Menu`, a `wp_update_nav_menu_item` handler, per-item meta such as an icon)?
- What does it seed on activation (terms, pages, menus, widgets, other posts, filled sidebars), and through which function? Does it have its own sample-content or one-click import system (a meta key tagging imported content, a tracked-settings option, remove or reset tools)?
- Which of its own functions or classes save, sanitize, seed defaults, or clear caches?
- Which transients or object-cache keys does it set, and what clears them?
- Does it make outbound HTTP requests (`wp_remote_get`, `wp_remote_post`, `wp_safe_remote_*`, `download_url`, `file_get_contents` or `curl` on URLs), and from which hooks: every page load, admin only, cron, or on demand? Which third-party hosts do its pages load files from (fonts, CDNs, embeds, analytics)?
- Does it have an update checker or license system (Envato, EDD, Freemius, a custom updater hooked to `pre_set_site_transient_update_themes` or `site_transient_update_themes`)? Record every host it contacts, what it sends, the timeouts, how results are cached, and where license keys are stored and shown.
- How does it handle versions: a stored version option, migration or upgrade routines, and what they change? What changed since the release chosen at intake question 7 (if any): renamed or removed options, meta keys, functions, hooks, template part paths, image sizes, and Customizer defaults?
- Does it store personal data (IP addresses, emails, names, user agents, per-visitor votes or likes) or set cookies, in PHP (`setcookie`) or JS (`document.cookie`, `localStorage`)? Does it register personal data exporters or erasers?
- What does it do on `switch_theme`, `after_switch_theme`, and `after_setup_theme` (on activation), and does it flush rewrite rules, and when?
- Which admin notices does it show, on which screens, to which roles, and how are they dismissed?
- Does it change uploads (`upload_mimes`, SVG support, `wp_handle_upload` filters), and does it handle any uploads or file writes itself?
- Does it output structured data (JSON-LD, microdata), Open Graph or Twitter tags, meta descriptions, or its own `<title>`?
- Which date and time functions does it use for display and comparisons (`date()`, `gmdate()`, `wp_date()`, `date_i18n()`, `current_time()`, `human_time_diff()`, `strtotime()`), and does it respect the site's `date_format`, `time_format`, and time zone?
- Which translation functions does it use, where does it call `load_theme_textdomain()` and on which hook, and does it call `wp_set_script_translations()` for its JS?
- Does it depend on plugins (WooCommerce, ACF, and so on)? What happens when one is missing: a notice, a fallback, or a fatal error?
- Does it have a build step for CSS or JS (Tailwind, Sass, PostCSS, webpack, Vite, Rollup, esbuild, Gulp, Grunt, `@wordpress/scripts`)? Record each script in `package.json` (and `composer.json` scripts), the config files it reads, its source and output paths, the Node.js version it asks for (`engines`, `.nvmrc`, `.node-version`), the package manager its lockfile belongs to, and whether the outputs are committed or ignored by `.gitignore`. Section 3's build step builds and tests it; never build inside the theme or overwrite its committed files.

**Templates and template parts**
- Every template file the hierarchy can load (`index.php`, `home.php`, `front-page.php`, `single-*.php`, `page-*.php`, `archive-*.php`, `taxonomy-*.php`, `category-*.php`, `author.php`, `search.php`, `404.php`, `attachment.php`, and the rest) and which URLs should reach each one; every page template (`Template Name:`, `Template Post Type:` headers).
- Every template part and how it's loaded: `get_template_part( $slug, $name, $args )` with the files it can resolve to (`<slug>-<name>.php`, then `<slug>.php`), `get_header()`, `get_footer()`, `get_sidebar()`, and `get_search_form()` with their named variants, `locate_template()` (with its `$load` and `$require_once` arguments), and plain `include` or `require` of theme files. For dynamic names (`get_template_part( 'parts/content', get_post_format() )`), list every value the name can take and the file each resolves to.
- For each part: the variables it uses and where each comes from (`$args`, globals such as `$post` and `$wp_query`, template tags, or variables it expects from the file that loaded it), the loop state it assumes (inside the loop, outside it, or a custom `WP_Query`), and the HTML it opens and closes.
- Core output hooks the templates must call: `wp_head()`, `wp_body_open()`, `wp_footer()`, `language_attributes()`, `body_class()`, `post_class()`, `comments_template()`, and `wp_link_pages()` in singular templates.

**Code structure**
- Is the theme procedural (plain functions with a prefix), class-based, namespaced, or a mix? Record each namespace and the files in it, every `use` import, and every `declare( strict_types=1 )`.
- How classes load: Composer autoload (`composer.json` `autoload`, PSR-4 or classmap, and whether `vendor/autoload.php` is committed and shipped), a custom `spl_autoload_register` loader and the file-name rule it applies, or plain `require` calls. Record which classes each loader should find.
- For each class: where it's instantiated and how many times (singletons, `::instance()`, a container, or `new` inside hooks), where its constructor adds hooks, and whether hooks use `$this`, static methods, or closures. Record interfaces, abstract classes, and traits, and what implements or uses them.
- For procedural code: the function prefix, which functions are wrapped in `function_exists()` so a child theme can override them, and every function defined inside a condition or another function.
- Every `global` variable the theme reads or writes, and every constant it defines, with where each is defined and used.

**Functions and entry points**
- Every function, class method, and closure the theme defines, and every place that calls it or hooks it (`add_action`, `add_filter`, `add_shortcode`, callbacks passed by string or array to `register_setting`, `add_meta_box`, `usort`, `array_map`, and so on).
- Every hook the theme adds, with its priority and `accepted_args`, and every `remove_action` / `remove_filter` with the priority it removes at.
- Every entry point that runs outside a normal template load: AJAX handlers (`wp_ajax_*`, `wp_ajax_nopriv_*`), REST routes (`register_rest_route`), shortcodes, widget classes, cron events (`wp_schedule_event`, `wp_schedule_single_event`), admin-post handlers (`admin_post_*`), rewrite rules and query vars, and filters on core behaviour (`pre_get_posts`, `the_content`, `excerpt_length`, `body_class`, `wp_nav_menu_args`, and the like).
- Everything the theme exposes or changes through the REST API: each `register_rest_route` with its methods, `args` (with `required`, `type`, `validate_callback`, `sanitize_callback`, `default`), `permission_callback`, and callback; `register_rest_field`; `show_in_rest` on its post types, taxonomies, and meta (`register_post_meta`, `register_term_meta`, `register_meta`), with the schema it gives; and filters on core REST behaviour (`rest_prepare_*`, `rest_endpoints`, `rest_authentication_errors`, `rest_pre_dispatch`, `rest_{$post_type}_query`).

**JavaScript**
- Every script and style the theme enqueues or registers: handle, file path, dependencies, where it loads (front end, admin, specific pages), and the data passed with `wp_localize_script` or `wp_add_inline_script`.
- For each theme JS file: the selectors it binds to, the AJAX actions and REST paths it calls, the localized keys it reads, the globals it expects (`jQuery`, `wp`, a library), and the functions it defines.
- The version argument each asset is enqueued with (a constant, the theme version, `filemtime()`, `null`, or `false`), and the browsers the theme supports (`browserslist` in `package.json`, `.browserslistrc`, or the readme).
- CSS: each stylesheet's purpose, `@media print` rules, animations and transitions, and whether any respect `prefers-reduced-motion`.

**Blocks**
- Every block the theme registers: `register_block_type` calls and `block.json` files, with each block's name, `apiVersion`, attributes (type, default, source), `supports`, `render` / `render_callback` (dynamic) or `save()` (static), every `file:` asset path (`editorScript`, `script`, `viewScript`, `style`, `editorStyle`), and any `deprecated` entries.
- For each block, which kind it is: **built** (JSX or ES modules compiled by a build step, with an `index.asset.php` listing dependencies), **no-build** (plain JS using the `wp.blocks`, `wp.element`, `wp.blockEditor` globals, registered with `wp_register_script` or a `block.json` pointing at an unbuilt file), **dynamic** (rendered on the server by a `render.php` file or `render_callback`, with `save()` returning `null` or inner blocks only, possibly previewed in the editor with `ServerSideRender`), **static** (markup saved by `save()`), or **PHP-only** (no editor script at all). Also note any `viewScriptModule` or Interactivity API use (`data-wp-*` directives, `wp_interactivity_state`).
- Patterns: every pattern file in `patterns/` with its header fields (`Title`, `Slug`, `Categories`, `Keywords`, `Block Types`, `Post Types`, `Template Types`, `Inserter`, `Viewport Width`, `Description`), every `register_block_pattern` and `register_block_pattern_category` call, patterns loaded from the Pattern Directory (`patterns` in `theme.json`), synced patterns (`wp_block` posts) the theme creates or ships as starter content, and patterns offered as starter content for new pages (`Block Types: core/post-content`). Record which images, template parts, and other patterns each one uses.
- Block styles (`register_block_style`) and block variations; blocks the theme unregisters or restricts (`allowed_block_types_all`, `unregister_block_type`, `should_load_remote_block_patterns`, `remove_theme_support( 'core-block-patterns' )`).
- `theme.json` (version, palette, font sizes, layout sizes, custom templates and template parts), `add_theme_support` calls for block features (`editor-styles`, `wp-block-styles`, `align-wide`, `responsive-embeds`, `editor-color-palette`, `editor-font-sizes`), and `add_editor_style` files.
- Block templates and parts (`templates/*.html`, `parts/*.html`, `block-templates/`) if the theme is a block or hybrid theme.
- Whether widget areas use the block widget editor or the theme forces classic widgets (`remove_theme_support( 'widgets-block-editor' )`).
- Record each block in the inventory like any other entry point, and each block attribute like a field in the data model (default, where it's rendered, and how it's escaped).

For every function, method, closure, and entry point, record one inventory row: name; defined at `file:line`; how it runs (called from `file:line`, or the hook, route, action, or shortcode name with priority and `accepted_args`); the parameters it takes; and a status column that section 3 fills in. The status is one of `Tested` (with how), `Read only` (with why it can't be run on the test site), `Unused` (nothing runs it; see section 2), or `Not read`. By the end of the audit no row may be `Not read`, and every `Read only` row needs a reason a reader would accept.

For every meta field, Customizer setting, and options field, record one table row: key (plus array key); storage (post, term, or user meta; theme_mod; option); field type; allowed choices or checked value (`'1'`, `'on'`, `'yes'`); date format; default, both where it is registered and where each template falls back; sanitize or save callback and the shape it stores (image controls may store a URL or an attachment ID); serialized or one row per value; where it applies (post types, formats, page templates, and conditions such as "paid items only"); where templates output it, and with which escaping function; what the template prints around the value (labels, units, prefixes); and what shows when it's empty (a fallback, or the element is hidden).

Summarize this data model and the inventory in markdown tables before you test anything, citing `file:line` for each item. Keep the data model and the inventory in `<work>/inventory.md` while you work; they become the coverage file (section 5) at the end.
