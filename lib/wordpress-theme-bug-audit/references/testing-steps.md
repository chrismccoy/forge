# Section 3, part 2: steps 1 to 11

Read this in full before step 1, and again after any context compaction before continuing. `<scripts>` is the `scripts/` folder beside `SKILL.md` (`${CLAUDE_PLUGIN_ROOT}/lib/wordpress-theme-bug-audit/scripts`); `testing-setup.md` explains each script. Mark each step done in the state file on its own, the moment it finishes, with the files that hold its evidence; never mark several steps done in one write.

As you go, build the two URL lists `version-pass.sh` replays for the other PHP versions: `<work>/urls.tsv` (front-end pages) and `<work>/admin-urls.tsv` (admin screens), one `<label><TAB><path>` per line.

1. **Activation.** Before writing anything, record what the theme seeded on activation, then run its seeder a second time (switch to another theme and back with `wp theme activate`) and check nothing is duplicated or overwritten. Grep `debug.log` for errors from activation.
2. **Empty site.** With `serve start`, fetch with `fetch.sh` the home page, a single post, a page, the search results for a term that matches nothing, a 404, and every archive the theme has, using core's default content only. Every empty state must render without PHP errors, placeholder text, or broken markup.
3. **Probe content.** Create 2 posts per post format and post type, a few terms per taxonomy, 2 users if the theme shows authors (one with a bio, one without), a page per page template with the exact slugs the templates expect, a menu in every registered location (with per-item fields filled through the theme's own handler), a widget in every sidebar, and a few threaded comments on post types that show them. On one item of each kind fill every field; on the other leave every optional field empty, so both states render. Then add edge cases, each as its own post of the default post type (and of any custom post type whose template differs):
   - a title of 200 characters with no spaces for 60 of them, and a post with no title at all;
   - a password-protected post, a private post, a scheduled post, and a sticky post;
   - a post split into pages with `<!--nextpage-->`;
   - a title and body with emoji, accented characters, `&`, `<`, and quotes, and one written in right-to-left text (Arabic or Hebrew);
   - a post with 100 tags and 10 categories, and a post with none;
   - an excerpt of 1,000 words, and a body that is a single unbroken URL;
   - enough posts in one category to reach 3 archive pages, and one post with enough comments to reach a second comment page (turn core's `page_comments` on for this).
4. **Save handlers.** Fill each meta field through the theme's own save handler, the way the edit screen would. If the handler reads `$_POST` and checks a nonce, call it with a temporary `$_POST` (and `$_REQUEST` where the handler reads that) holding your values and a real nonce from `wp_create_nonce()` for its action, then restore the originals. If the handler lives in a file the theme loads only in wp-admin, `require_once` that file first, because `wp eval-file` doesn't load it. For ACF write with `update_field()` using field keys. Then read back each value with `wp eval` and compare it with what the template reads. Also save once with every checkbox unchecked and confirm each one actually clears. Do the same for every term, user, and attachment field through its own handler: create a term with every field filled through the add-form hook, edit it through the edit-form hook, then run a quick edit on it (post to `admin-ajax.php` with `action=inline-save-tax` and the `taxinline` nonce, over HTTP with `-b <tmp>/jar`) and confirm its meta survives. Run a quick edit (`action=inline-save`, `_inline_edit` nonce) and a bulk edit on a probe post and confirm its meta survives too. Delete a probe term and a probe post and confirm their meta, and any term options, are gone.
5. **Sanitizers.** For each Customizer setting and options field, write a valid value and then an invalid one (a choice not in the list, an out-of-range number, a malformed colour, `<script>` in a text field, an empty required field), and record what is stored. Use the Customizer route: load `wp-includes/class-wp-customize-manager.php`, create `$GLOBALS['wp_customize'] = new WP_Customize_Manager()`, then move every `customize_register` callback at priority 10 that doesn't belong to the manager to priority 11 (the theme hooked in before the manager existed, so its callbacks would otherwise run before core registers `blogname` and the other core settings, and a theme that calls `get_setting( 'blogname' )` would fatal), then fire `do_action( 'customize_register', $GLOBALS['wp_customize'] )`, then `set_post_value( $id, $value )` and `get_setting( $id )->save()` for each, and fire `do_action( 'customize_save_after', $GLOBALS['wp_customize'] )` once at the end. If `get_setting( $id )` returns null, the template reads a mod with no control: that's a bug from section 2. For an options panel, submit through the theme's own `register_setting` sanitize callback or framework, and confirm keys on other tabs survive. Finish with valid values in every field, every show or enable switch turned on, so every output path renders in the next step. Never write to code or secret fields (custom CSS or JS, header or footer scripts, analytics IDs, API or license keys); list them instead. Then test each options page over real HTTP, the way the form submits it: fetch the page with `-b <tmp>/jar`, and find how it really submits (the form's `action`, `method`, and hidden fields, and any JS that rewrites the submission; frameworks such as Carbon Fields post compact JSON to `admin.php` with the nonce inside it, not `options.php`). For a plain settings form, take the `_wpnonce`, `option_page`, and field names from it, post the form to `options.php` with changed values, and confirm the change is stored and shown after the redirect, with no "options page not found" error. Do this for each tab separately and confirm the other tabs' values survive. Run the reset, import, and export tools if the theme has them, and check what each one changes. For the Customizer, render every selective refresh partial's `render_callback` through `wp eval` and compare it with the matching markup on the front end; check that every `postMessage` setting has a binding in the preview script (and that every binding names a real setting); and evaluate every `active_callback` both ways. For each colour setting the theme puts text on or under, save its default, then `#ffffff`, then `#000000`, and check the pages that use it with the step 9 axe `color-contrast` rule; a failure with the default or with a preset the theme offers is a bug, and a failure only with a free choice is a bug only if the theme claims to adjust text colour for contrast.
6. **Front end.** Fetch the home page, every sort or filter mode the theme has, every archive type it has, one single view per format and post type (both the filled and the empty item), each page template, search results, and a 404. Confirm each returns 200, contains the markup the templates output for each feature, shows each probe value where the data model says it appears, and has no PHP errors in the HTML, `<tmp>/server.log`, or `debug.log`. Check the value from step 5 with `<script>` in it comes out escaped. Also fetch each edge-case post from step 3 (logged out and logged in), page 2 of the split post, page 3 of the long archive, an archive page number past the last one (it should 404 cleanly), and the second comment page. Then read `<tmp>/queries.log`: a query the theme repeats once per post in a loop, the same query run several times on one page, or a count that grows with `posts_per_page` is a bug (Low, or Medium if it runs on every page). Then read `<tmp>/templates.log`: every part request that resolved to no file is a bug, and every template and template part in the section 1 list must have rendered on at least one URL; for any that didn't, find a URL or probe item that reaches it and fetch it, or give the reason no URL can (in the coverage file). Check the saved pages with `html-check.py` (and with `vnu` from `<tools>/node_modules/vnu-jar` if Java is installed), and trace each structural problem to the template or part that caused it.
   Follow every link, tab, sort control, filter, and pagination link the theme outputs on these pages at least once, and every sortable column and row action on the theme's admin list screens in step 7, and record the status code and whether the result makes sense (a sort that empties the list, a tab that 404s, a filter that ignores its value). A page that loaded isn't a feature that works. Also fetch: the main feed (`/feed/`), the comments feed, a category feed and a feed for each public custom post type; `/wp-sitemap.xml` and each sub-sitemap it lists; the `/embed/` view of a post; an attachment page; and the page that shows each theme feature with print styles if the theme ships any. Run `<scripts>/assets-check.py "$WP_TEST_URL" <out-dir>` on the saved pages: the test server answers some missing static files with an empty 200 page instead of a 404, so a missing stylesheet or script (a theme's `style-rtl.css`, for example) never shows as a 404; this fetches every local asset the pages load and reports any that are missing, empty, or served with the wrong type. Run it again after each variation that changes which assets load (right to left, child theme). Grep the theme's CSS files, including bundled library CSS, for `@import` and `url()` pointing at other hosts, which `html-check.py` can't see. From `html-check.py`'s report, check every JSON-LD `@type` has the properties search engines require, list the third-party hosts each page loads files from, and check the theme's `<img>` tags (no `alt`, no size, a lazy first image); also check `srcset` and `sizes` on the theme's images, and record every cookie each page sets (`curl -c`). Read `<tmp>/requests.log`: any request made while rendering a normal front-end page is a bug unless it's cached and rare.
7. **Admin.** Run `login`. Load one edit screen per post type and page template, the add and edit screens and list table of every taxonomy with theme fields, a user profile screen if the theme adds fields, the media edit screen if it adds attachment fields, `customize.php`, each options page and tab, the menus screen, and the widgets screen. Confirm there are no PHP errors, each saved value shows in its field, and nothing needed for editing is missing. Load `customize.php` with `shot`, logged in through `login-js.sh` and with `capture.js`, so broken custom controls show up; if it doesn't finish loading in time, mark that check SKIPPED and read the control scripts instead. Do the same for each options page and each term edit screen that loads a picker or uploader script. For every admin script call JS-06 lists, trigger the user action behind it on a probe post with a featured image and meta, then reload and check nothing else on the post changed. Record every admin notice the theme shows, on which screens, and whether dismissing it (following its dismiss link or AJAX call) keeps it gone on the next load, for the same user and another admin. Time each admin screen with `curl -w '%{time_total}'` and read `<tmp>/requests.log` for requests made while loading admin screens.
8. **Entry points.** Run every entry point in the inventory, first with valid input, then with bad input (a missing or wrong nonce, a logged-out request to a logged-in-only action, missing or malformed parameters, an ID that doesn't exist), and record the status code, response body, and any PHP errors.
   - **Public endpoints:** for every endpoint SEC-14 covers, send the same action 20 times quickly from one client, send nonexistent, draft, private, and wrong-post-type IDs, send it with the theme option for that feature turned off, and clear or forge its dedupe cookie between calls; record what changed each time.
   - **AJAX and admin-post:** `curl` to `$WP_TEST_URL/wp-admin/admin-ajax.php` or `admin-post.php`, with `-b <tmp>/jar` for logged-in requests and without it for logged-out ones. Take the nonce from the page the feature lives on (the `wp_localize_script` data in the HTML fetched with the same cookies), because a nonce made with `wp eval` belongs to a different session and fails.
   - **REST:** list the routes with `wp eval 'echo implode( "\n", array_keys( rest_get_server()->get_routes() ) );'` and check that each of the theme's routes is registered. Call each route and method with `wp eval` through `rest_do_request( new WP_REST_Request( '<METHOD>', '<route>' ) )`, once with `wp_set_current_user()` set to an administrator, once as a subscriber, and once as user 0; for each, send valid parameters, then missing required ones, wrong types, and an ID that doesn't exist, and record the status code and response body. Check that `permission_callback` blocks what it should, and that errors come back as `WP_Error` with a 4xx status. Then call each route over HTTP with `curl` at least once logged out and once with `-b <tmp>/jar` and the `X-WP-Nonce` header (the `wp_rest` nonce from the page's localized data), because `rest_do_request` skips cookie and nonce checks. Also fetch the core routes for the theme's post types, taxonomies, and users (`/wp/v2/<rest_base>`, `/wp/v2/users`) logged out, and check that no meta or field the theme registers leaks private data there, and that meta with `show_in_rest` reads and writes in the shape the theme stores.
   - **Shortcodes:** run each through `do_shortcode()` with typical attributes and with none, and put one in a probe post to fetch on the front end.
   - **Widgets:** render each widget class with `the_widget()` with an empty instance and a filled one, and save one through its `update()` method.
   - **Cron:** WP-Cron is off on the test site, so list events with `wp cron event list` and run each theme event with `wp cron event run <hook>`; also check that loading a page twice doesn't add a second copy of any event.
   - **Core filters and other functions:** for each filter on core behaviour, name the page where its effect should show and confirm it there. Call any function the inventory still shows as unreached directly with `wp eval`, with typical input and edge input (empty string, `0`, `null`, a post ID that doesn't exist).
   - **Update checker and license:** if the theme has one, add a must-use plugin that makes `pre_http_request` return a `WP_Error` for its hosts, then load the Dashboard, Themes, and Updates screens and run `wp theme list --update=available`; any PHP error, a load time above a few seconds, or a request repeated on every load is a bug. Remove the plugin, then make the same hosts answer with an empty 200 response and then with invalid JSON, and check again. Check the `update_themes` site transient's entry for the theme has the right key and fields. Never contact the real license server with a real key.
   - Update each inventory row's status as you go.
9. **JavaScript.** Capture JS errors, failed requests, and accessibility violations on every page from step 6 and every admin screen from step 7, at 1440 and 390 wide, by running `shot` with `capture.js` as `SHOT_INIT_JS` (and `login-js.sh` for admin screens). Summarize with `jslog.py <tmp>/server.log <slug>`, which also lists 404s on theme files (missing scripts, styles, fonts, images). For each interactive feature (menu toggle, search overlay, tabs, slider, modal, load-more, like button), append code after `capture.js` that waits for `load`, then clicks, focuses, or presses keys on the element, and reports what happened (including `aria-expanded` and where focus went) with `window.__auditSend( 'ix', … )`. `shot` captures about 3 seconds after `load`, so `capture.js` sends `__axetimeout` if axe hasn't finished 2.5 seconds after load, and `jslog.py` lists those pages: run axe again on them one region at a time (prepend `window.__AUDIT_AXE_CONTEXT = 'main';`, then `'header'`, `'footer'`). A page with neither `__axedone` nor `__axetimeout` never reached `load` before the capture. Including `capture.js` twice is harmless. Report violations the theme's markup or CSS causes; ignore ones that come from core or probe content. If `shot` exits with code 3, mark this step SKIPPED and fall back to reading the JS against the HTML the pages output.
10. **Sample-content system.** If the theme has a sample-content or one-click import system, run its remove or reset tool once and record what it removes and what it leaves.
11. **Screenshots.** If `shot` exits with code 3, mark this step SKIPPED with the reason it printed and carry on. Otherwise take the home page, one archive, and both single views of each kind at 1440, 1024, 768, and 390 wide, plus the home page and one single view at 720 wide (standing in for 200% zoom at 1440), save them in `<work>/shots/`, and look at each one. Report visual bugs: text overflowing its box, overlapping elements, badly cropped images, sections that look broken or empty when they have data. If an overlay (age gate, cookie wall) covers the pages, take one pair with it showing, then bypass it with `SHOT_INIT_JS` (setting the cookie or storage flag it checks) for the rest. If pages show explicit or otherwise unsuitable content (bundled adult ads, for example), don't describe it: check the layout by measurement instead and say so. When something looks wrong, measure it rather than guessing: `SHOT_INIT_JS` can log `getBoundingClientRect()` or `document.elementFromPoint()`. If you can't view images, say so and mark the review SKIPPED. Keep the screenshots that show a bug in `<work>/shots/`, tagged with the candidate bug; copy them into the evidence screenshots folder (section 5), named `<bug-number>-<page>-<width>.png`, only after section 4's independent check, when bug numbers are final.
