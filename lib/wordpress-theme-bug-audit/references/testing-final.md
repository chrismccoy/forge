# Section 3, part 4: steps 13 to 17

Read this in full before step 13. Mark each step, and each PHP version in step 13, done in the state file on its own, the moment it finishes.

13. **Versions.**
    - **PHP versions:** for every version in the intake question 2 list other than the primary one, one at a time, run `bash <scripts>/version-pass.sh <work> <theme-dir> <php-minor>` (with `AUDIT_MEDIA_DIRS` set as for every site). It lints every theme file with that PHP, builds a site on it, replays `<work>/probe/` (the numbered PHP and shell scripts, including the valid-input step 8 calls you saved as `.sh` files), logs in, fetches `<work>/urls.tsv` and `<work>/admin-urls.tsv`, runs `<work>/probe/loading.php` (step 16) if present, collects the PHP errors from the pages, `debug.log`, and `server.log` into `<work>/php-<version>-errors.txt`, and tears the site down. Then run `capture.js` on the home page and one single view on that version too, if the version's JS behaviour could differ (it rarely does; one width is enough). Compare the versions: an error, warning, or deprecation that appears on some versions and not others is a bug that names those versions, and a deprecation on the newest versions is a bug too, because it becomes an error in a later release. Tear each site down before the next. If a version is BLOCKED, say so in the report and rely on its code-only checks.
    - **Oldest WordPress:** use the version from intake question 8. Run it on the newest PHP in the list that WordPress version supports (the pairing rule in PHP versions; for example WordPress 6.4 doesn't run on PHP 8.5), with `version-pass.sh <work> <theme-dir> <php-minor> <wordpress-version>`, which installs that version, updates the database, and resets the admin password (newer WordPress stores password hashes older versions can't read). Its fetches cover steps 6 and 7: a call to a function or argument newer than that version is a bug. Tear that site down afterwards. Mark whatever you can't run SKIPPED with the reason.
14. **Upgrade.** Skip this if intake question 7 said to. Put the earlier release in `<work>/prev/<same-folder-name>/` (`git worktree add` for a tag, unzip a zip, or copy a folder with `rsync -a`, leaving out media folders). Build a new test site from that copy with `new-site.sh`, then run steps 3, 4, and 5 against it with the saved probe scripts, adjusted to the fields that release has, and dump every theme option, theme mod, and the post, term, and user meta of the probe items to `<work>/upgrade-before.json`. Replace the site's copy of the theme with the current theme (`rsync -a --delete` from `<theme-dir>`, with the same exclusions `new-site.sh` uses, then re-link the media folders), restart the server (`serve stop`, then `serve start`: the running `php -S` caches file paths and would serve old files), load the home page and the Dashboard once, then dump the same data to `<work>/upgrade-after.json` and compare. Settings or meta that disappeared or changed without a migration, errors during the first load, a migration that runs again on the second load (check the version option and `<tmp>/queries.log`), and front-end or admin pages that break are bugs. Diff the two releases' function, hook, template part, and image size lists from section 1 and report removed or renamed public ones that the changelog doesn't mention. Tear this site down with `site-down.sh` afterwards.
15. **Standards.** On the main test site: install the Theme Check plugin (`wp plugin install theme-check --activate`), find its entry function by reading its code (it runs every check against a theme object), and run it with `wp eval` against a separate copy of the theme in `<work>/themecheck/<same-folder-name>/` made with `rsync -a`, leaving out `audit/`, folders the theme doesn't ship, and the media folders entirely (a linked media folder would be scanned file by file), and record every `REQUIRED`, `WARNING`, and `RECOMMENDED` result; treat `REQUIRED` and `WARNING` results as candidate bugs, and put the rest in the coverage file. Build a fresh `.pot` with `wp i18n make-pot <theme-dir> <work>/fresh.pot --slug=<slug> --domain=<text domain>` and compare its `msgid` list with the shipped `.pot`. List the theme's autoloaded options and their sizes (`wp option list --autoload=on --format=json`, then filter by the theme's prefix and option names from section 1) and transients with no expiry. If intake question 6 chose a marketplace, check its rules from section 2 (`MKT`) now.
16. **Loading.** Write this as `<work>/probe/loading.php`, so `version-pass.sh` repeats it on every PHP version, and run it with `wp eval-file`: `class_exists( '<fully qualified name>' )` (and `interface_exists`, `trait_exists`) for every class, interface, and trait in the inventory, so each one's autoloading is proven on Linux's case-sensitive file system; `function_exists()` for every function; and a scan of `$GLOBALS['wp_filter']` for theme callbacks registered more than once on the same hook and priority, which shows classes instantiated twice. Then, in one `wp eval`, call the theme's setup function, its main class constructor, or `::instance()` a second time, and check for "Cannot redeclare" errors and duplicate hooks. With the blank child theme from step 12 active, define one overridable function in its `functions.php` and confirm the child's version is the one that runs.
17. **Coverage and teardown.** Go through the inventory: every row must be `Tested`, `Read only` with a reason, or `Unused`. If line coverage ran, merge it now: a function whose lines never ran must be run now, marked `Unused`, or given a `Read only` reason. Run whatever is still unreached, then read `debug.log` in full one last time and tear the site down with `site-down.sh`. Check no `php -S` process is still serving a folder under `<work>/sites` (`ps -C php -o pid=,args= | grep -F -- '-S 127.0.0.1'`, which can't match its own command line the way `pgrep -f` does); stop any that is, by PID. Mark the run finished in the state file. Keep `<work>` until section 6 is done or I decline fixes, then delete everything in `<work>` except the state file, `findings.md`, the notes, the probe scripts, and the URL lists: that includes `tools/`, `build/`, `prev/`, `themecheck/`, `pages/`, `shots/`, `sites/`, every `phpstan-*/` folder, and any `_prev-*` archive. Check the folder's size with `du -sh <work>` afterwards (it should be a few MB), and before you report, remove any `wp-theme-audit-*` containers still running, and tell me the `wp-theme-audit-php:*` images you built (keep them for later runs unless I ask you to remove them), and tell me the path of what's left (the state file, notes, and probe scripts).
