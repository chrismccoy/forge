# Section 3, part 1: the test environment

Read this in full before the first site step, and again after any context compaction before continuing section 3. `<scripts>` means the `scripts/` folder beside `SKILL.md` (`${CLAUDE_PLUGIN_ROOT}/lib/wordpress-theme-bug-audit/scripts`); every script prints its usage when run without arguments, and its header comment explains what it does.

## Safety

- Always test in a throwaway WordPress, even if a WordPress site is reachable from here. Never run `wp` write commands against the site this theme is installed in, and never read or reuse that site's `wp-config.php` or database credentials.
- Never use `sudo`, never install anything globally or inside the theme, and never use `pkill -f`, which can kill your own shell. Stop a process only by a PID you've checked belongs to your own test site.
- Take screenshots only with `shot`, one at a time. Don't use Playwright or browser automation tools: a runaway headless browser can use several GB and take the whole machine down.
- **Disk space.** `new-site.sh` refuses to build a site with less than 1 GB free. Check `df -h` on the disk holding `<work>` before any other step that creates files too (the build, extra copies). If free space drops below 1 GB, stop, write the state file, and report. Tear each extra site down as soon as its step is done.
- **Media folders.** `<scripts>/media-dirs.sh <theme-dir> --report` lists the theme's media folders: at least 10 MB, at least 90% images, video, audio, or fonts, and no code at all, so linking one can never hide code. Media folders are never read file by file and never copied. `new-site.sh` detects and links them automatically (and links any media file over 1 MB, and any file over 5 MB); set `AUDIT_MEDIA_DIRS` yourself only to override the detection. Leave them out of every other copy too (the build copy, the Theme Check copy, the upgrade copy). Record each in the manifest as excluded, with its size, and check the images the theme outputs through the pages instead (broken URLs show up as 404s).

## Tools

Run `<scripts>/install-tools.sh <tools>` once (`<tools>` = `<work>/tools`). It installs phpcs with WordPress Coding Standards and PHPCompatibility 10 (which has the PHP 8 checks; it says so plainly if only 9.x installs), PHPStan with the WordPress extension (Composer's plugin permissions are set before installing, so the WordPress stubs load), ESLint, stylelint, axe-core, and the vnu validator, and prints each tool's version or MISSING. Mark the checks that need a MISSING tool BLOCKED and carry on. Tools only used if already on the machine: Xdebug or pcov (line coverage), Docker (PHP 7.x), and Java (vnu). Never install PHP extensions, PHP versions, or Docker.

## Static analysis

Run these before the site steps, with `AUDIT_EXCLUDE_DIRS` set to the folders the theme doesn't ship (all three scripts honour it). Treat every result as a candidate bug: confirm it by reading the code, and record dropped false positives with reasons in the coverage file. Keep full output in `<work>`; bring only counts and the lines you need into the conversation.

- **PHPStan:** `<scripts>/phpstan-batches.sh <tools> <theme-dir> <php-minor> <work>/phpstan-<php-minor> [level]`, once per PHP version in the intake list. It analyses about 8 files per run with the whole theme in `scanDirectories`, under memory caps, because PHPStan's defaults crashed a 6 GB machine. Put a `bootstrap.php` defining the theme's constants in the output folder first, and add stubs for any plugin the theme depends on to `<tools>` (for example `php-stubs/woocommerce-stubs`, `php-stubs/acf-pro-stubs`) so their functions aren't reported as undefined. Level 5; if it's clean, try 6 and report what it adds.
- **phpcs, correctness only:** `<scripts>/phpcs-correctness.sh <tools> <theme-dir> <text-domain> <oldest-wordpress> <oldest-php>-<newest-php> <work>/phpcs`. Security (escaping, nonces, input sanitizing, safe redirects), prepared SQL, text domain, deprecated WordPress functions, and PHP compatibility; no style rules. PHPCompatibilityWP knows which functions WordPress polyfills, so those aren't flagged.
- **ESLint and stylelint:** `<scripts>/lint-js-css.sh <tools> <theme-dir> <work>/lint [globals the theme's localized scripts define]`. Real errors only; stylelint checks unsupported browser features against the theme's `browserslist` (or `defaults`).
- **block.json:** if the theme has any, check each against the schema its `$schema` key names (install `ajv-cli` in `<tools>` if you can reach the schema; otherwise check the required keys and every `file:` path by hand).

## Build

If section 1 found a build step, test it before the site steps, in `<work>/build/<same-folder-name>/` (the same folder name keeps the theme's slug). Make that a real copy of the theme's source, leaving out `node_modules/`, `.git/`, `audit/`, and media folders (`rsync -a --exclude …`): symlinked sources break bundlers such as esbuild.
- **Install** with the package manager the lockfile belongs to (`npm ci`, `pnpm install --frozen-lockfile`, `yarn install --frozen-lockfile`), under the Node.js version the theme asks for if it's installed; otherwise use the one on the path and say which. Record install errors and a lockfile that doesn't match `package.json`.
- **Run** each build script the theme documents (`build`, `production`, `dev` if that's the only one), saving the full output. Record whether it succeeds, and every error and warning about missing files, unknown options, or deprecations.
- **Compare with what's committed:** for CSS, compare selector lists (`grep -o '[^{}]*{' file | LC_ALL=C sort -u` on both, then `LC_ALL=C comm`; with native nesting, compare class names with `grep -oE '\.[A-Za-z0-9_\\:/-]+' file | LC_ALL=C sort -u`). For minified JS, check that distinctive strings from the source (selectors, AJAX action names, REST paths, localized keys, user-facing strings) are in both the build and the committed file. List output files the build creates that aren't committed, and committed ones it no longer creates.
- **Class coverage:** for Tailwind or any other class scanner, extract every class name the PHP templates and JS use and check each exists in the built CSS. Look for class names built at runtime, which no scanner can find.
- Never copy build output into the theme. Keep the build for the "Rebuilt assets" variation.

## Test sites

Build every site with `new-site.sh`, never by running `setup-test-site.sh` directly:

```
tmp="$(AUDIT_MEDIA_DIRS='assets/gif' <scripts>/new-site.sh <work> <theme-dir> local)"   # or a PHP minor such as 8.1
source "$tmp/env.sh"
```

It runs `setup-test-site.sh` (WordPress on SQLite, WP-Cron off, `WP_DEBUG`, `WP_DEBUG_LOG`, and `WP_DEBUG_DISPLAY` on, pretty permalinks, the Classic Editor plugin), then:
- **copies the theme for real**, like a normal install. A symlinked theme breaks code that includes files or builds URLs from `__DIR__`, because PHP resolves `__DIR__` to the symlink's target. Only media folders and files over 5 MB are linked. After the theme's files change (in section 6), build a new site.
- **installs the audit must-use plugins** from `<scripts>/mu/`:
  - `audit-logs.php` logs one JSON line per request to `<tmp>/queries.log` (query count, and every query run more than once with its caller), `<tmp>/templates.log` (the template chosen, every template part requested and the file it resolved to or none, and every `get_header`, `get_footer`, and `get_sidebar` call), and `<tmp>/requests.log` (every outbound HTTP request with its caller, timeout, `sslverify`, and result). It blocks every outbound host except WordPress.org and the site itself, so the test site never talks to a vendor's real update, license, or API servers. Allow a host with `AUDIT_ALLOW_HOSTS` (comma-separated, exported before `serve start`) only when a step needs a third-party content API, and say so in the report.
  - `audit-vendor-notices.php` counts deprecation notices from files under a `vendor/` folder into `<tmp>/vendor-notices.log` instead of printing them. With `WP_DEBUG_DISPLAY` on, printed notices break redirects and status codes and hide the theme's own behaviour. Record them once as a bug with their counts. Notices from the theme's own files are never hidden.
- sets `SAVEQUERIES`, copies axe-core into the web root for `capture.js`, sets `PHP_CLI_SERVER_WORKERS=4` (`php -S` otherwise serves one request at a time, so a feature that requests the site's own URL hangs), and, with a PHP minor, runs the site on a standalone build from `php-static.sh`. With a WordPress version as the fourth argument, it installs that version, updates the database, and resets the admin password.
- for a child theme, set `AUDIT_PARENT_DIR` to the parent's folder.

Then install and activate every plugin the theme depends on; if one can't be installed, mark its checks BLOCKED. Extra plugins from intake question 3 are installed but stay inactive until the variations.

After `source <tmp>/env.sh`: `wp …` (WP-CLI pinned to the site; pass file arguments as absolute paths), `serve start` / `serve stop` / `serve status` (logging to `<tmp>/server.log`), `login` (admin cookie jar at `<tmp>/jar`), `shot <url> <file.png> [width] [height]` (headless Chrome; exits 3 if Chrome or Node.js 22+ is missing). Tool shells often don't keep state, so source `env.sh` in every command, or call `<tmp>/bin/<name>`. Always build URLs from `$WP_TEST_URL`.
- **Always `serve stop` before `serve start`:** a second start leaves the first server running.
- **Tear down with `<scripts>/site-down.sh <tmp>`,** never the bare `teardown`: it also stops any server still serving that folder and removes the folder.

If a site can't be built, `new-site.sh` removes the half-built site itself and names the log to read (`<work>/sites/setup-*.log`). Fix the cause only if it's in your environment (a missing PHP extension, for example); otherwise mark testing BLOCKED with the error and deliver the static findings from sections 1 and 2. Don't edit `setup-test-site.sh`; check it with `sha256sum` (it must print `bf82f7f6a2f6a2ce98fd2693e191938d3273a511da494f8f5a4b822d25adfd23`).

## PHP versions

The whole audit runs on one primary PHP version: the machine's own `php` if it's in the intake question 2 list, otherwise the newest version in the list. Every other version gets the step 13 pass (`version-pass.sh`). Where each version comes from:
- **Installed on the machine:** a matching `/usr/bin/php<version>`.
- **Standalone build, PHP 8.0 and later:** `new-site.sh` and `version-pass.sh` fetch it with `php-static.sh` into `<tools>/php/<minor>/`, with a 512 MB memory ini (the builds have no `php.ini` and default to 128 MB, too little for WP-CLI). They're built against musl libc, like Alpine Linux: `GLOB_BRACE` isn't defined, and some GD builds lack JPEG. A theme that uses `GLOB_BRACE` fatals on them, which is a real bug for customers on Alpine-based hosting and containers. Report it once, then add a test-only shim (a must-use plugin on the throwaway site, never a change to the theme) so the rest of the pass can run, and say so. They also answer 404 for some `.xml` and `.txt` routes; check sitemaps and `robots.txt` on the primary version.
- **Docker, any version and the only way to get PHP 7.x:** only if `docker info` works without `sudo`. Build an image `wp-theme-audit-php:<version>` from `php:<version>-cli`, with a Dockerfile in `<work>/docker/<version>/` that installs `curl`, `unzip`, `rsync`, `ca-certificates`, `bash`, and `python3` (`new-site.sh` runs `media-dirs.sh`, which needs it), the `gd` extension with JPEG and FreeType support, and the `zip` extension, plus an ini with `memory_limit=512M`. Run one container per version: `docker run -d --init --network host --name wp-theme-audit-<version> --user "$(id -u):$(id -g)" -e HOME=<work>/home -v <theme-dir>:<theme-dir>:ro -v <work>:<work> -v <scripts>:<scripts>:ro -w <work> wp-theme-audit-php:<version> sleep infinity`. Run `new-site.sh` and `wp` inside with `docker exec`, and `curl` and `shot` on the host against `$WP_TEST_URL` (the container shares the host's network). Never use `--privileged`, never mount anything else, and `docker rm -f` the container when its pass is done.
- **None of these:** mark the version BLOCKED, and still run its code-only checks (PHPStan `phpVersion` and phpcs `testVersion`).
- **WordPress pairing:** use the newest WordPress whose minimum PHP is at or below that version (the `php_version` field in `https://api.wordpress.org/core/version-check/1.7/`), passed to `new-site.sh` as its fourth argument if it isn't the latest.

## Line coverage

If Xdebug or pcov is already installed, record which theme lines run during every step. Point `PHP_INI_SCAN_DIR` at a folder in `<tools>` with an extra `.ini` (prefix it with `:` so PHP still reads its default folder, for example `export PHP_INI_SCAN_DIR=":<tools>/ini"`) that turns coverage on (`pcov.enabled=1` and `pcov.directory=<the site's copy of the theme>`, or `xdebug.mode=coverage`) and sets `auto_prepend_file` to a small PHP file that starts coverage and, on shutdown, writes that request's covered lines for theme files to a new JSON file in `<work>/coverage/`. Export it before `serve start` and before every `wp` command, in every shell. At the end, merge the files, and for every function in the inventory report whether any of its lines ran. If neither extension is there, mark line coverage SKIPPED and rely on the inventory statuses.

## Probe data

Write probe data as numbered PHP files in `<work>/probe/` (`01-content.php`, `02-options.php`, …), run with `wp eval-file`, and shell scripts for HTTP requests as numbered `.sh` files there too (`version-pass.sh` replays both in order, with `TMP` set to the site folder). Always real files: `wp eval-file` given a process substitution like `<(…)` silently prints nothing.
- It exists only to make every template branch run; it doesn't need to be realistic, but every value must be valid for its field.
- Give every probe post, page, and term an explicit slug (`post_name`, `slug`), and list URLs in `urls.tsv` by slug, never by ID or by a slug WordPress generated: IDs and generated slugs (`/32-2/`) differ on each fresh site, so the version passes would fetch pages that don't exist.
- Write it in PHP 7.4 syntax (no `match`, named arguments, nullsafe operator, enums, or `readonly`) unless the intake list starts higher, so it runs on every version.
- **Probe scripts that change state for a test** (a reset, a quick edit, a deletion) must put it back before they finish, because `version-pass.sh` replays every probe on each PHP version in order, and later probes and fetches expect the state the earlier ones built. Put destructive tests in their own scripts, after the ones that build content.
- **Every probe script checks its own writes and fails loudly:** read each value back and `exit( 1 )` with a message if it didn't stick. Save handlers that live in admin-only files aren't loaded by `wp eval-file`, so `require_once` those files first; a probe that "succeeds" without saving anything wastes every later step.
- Make no outbound requests for it. Generate images locally with GD as PNG files (some standalone builds have no JPEG; don't call `imagedestroy()`, deprecated from PHP 8.5) at least as large as the biggest registered crop the slot feeds, at the slot's aspect ratio, and sideload them from disk. Use `https://example.com/` for URLs, and for embeds one well-known YouTube URL and a `.mp4` URL on `example.com`.

## Rules for every step

- Queries run on SQLite through a translation layer, not MySQL; say so in the report. Inspect data with `wp eval` only, because `wp db` commands expect MySQL. Theme SQL that only MySQL accepts fails here: record it (a real bug only if the theme claims to support other databases), and add a test-only shim if you need the feature working to test the rest.
- **Never print whole pages or logs into the conversation.** Fetch pages with `<scripts>/fetch.sh <tmp> <out-dir> <label> <path> [curl args]`, which saves the body and prints the status, a count of PHP error lines, and whether WordPress printed "There has been a critical error" (a fatal doesn't always change the status code, so never rely on the status alone). `fetch.sh` sends a browser user agent by default, because WordPress serves some screens differently to other clients (the classic editor loads TinyMCE only for browsers). Check that the assets the pages load really exist with `<scripts>/assets-check.py "$WP_TEST_URL" <out-dir>`. Check saved pages in bulk with `<scripts>/html-check.py <out-dir> <out.json>` (unclosed and stray tags, duplicate IDs, invalid JSON-LD, third-party hosts, images without `alt` or size); it stands in for vnu when Java is missing.
- In `debug.log`, search for the theme's files by the site copy's path. Ignore lines from WP-CLI's own files, and lines core writes from `wp-includes/` unless the theme's call caused them.
- **Waiting for a background command:** wait on its process ID (`wait "$pid"`, or `while kill -0 "$pid" 2>/dev/null; do sleep 5; done`), never with `pgrep -f '<text>'`: the waiting shell's own command line contains that text, so it matches itself and the wait never ends. Before reporting, check that no background shell or command you started is still running.
- If a step can't run (no network, a missing tool), mark it BLOCKED with the reason. Never report a step as passed unless you ran it. Don't spend more than about 3 attempts or 15 minutes on one failing step; mark it BLOCKED with what you tried and move on.
- **Screenshots, JS errors, and accessibility:** pass `<scripts>/capture.js` as `SHOT_INIT_JS` (`SHOT_INIT_JS="$(cat <scripts>/capture.js)" shot …`). It reports JS errors, failed resources, and axe-core violations as requests the server logs; summarize them with `<scripts>/jslog.py <tmp>/server.log <slug>`. For logged-in pages, prepend `<scripts>/login-js.sh <tmp>/jar`'s output and open `?audit_target=<url-encoded target>` on any front-end URL. Append your own interaction code (clicks, key presses) after `capture.js` and report through `window.__auditSend( 'ix', message )`.
