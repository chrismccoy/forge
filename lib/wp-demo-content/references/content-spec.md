# Step 2 - what the importer must create

The theme decides what applies. Anything here the theme does not have is skipped, gets no
data, and is listed in the report - that is not a problem.

### Content

- **Posts:** the `POST_COUNT` input, spread across every format and post type the theme supports, with at least 3 of each; if that needs more than `POST_COUNT`, raise it and say so in the report. The count includes custom post types that show on the site or inside other content (sponsors, ads, partners), but not private or form-storage types. Order the items so every counted format, content kind, and post type rotates together, so `count=N` with N equal to the number of kinds gives one of each. If the theme has no post formats, rotate the content kinds its templates render differently (for example gallery, video, image, text-only). A post type that only ever appears inside other content as one card (an ad, sponsor, or partner block) needs 3 to 6 items rather than an equal share, so weight the rotation to keep those items occasional while `count=N` still gives one of each kind. The rotation covers the kinds the templates render differently, not every optional flag: a fallback state (an item with no video on a video site) and a flag such as "premium" get the occasional-field share, a few items each, not a quarter of the feed.
- **Post text:** a hand-written, believable title and a one-line blurb stored as `post_excerpt`. Write the body as classic-editor HTML with no block markup: `<p>`, plus `<h2>`, `<ul>`, and `<blockquote>` for standard posts, and shortcodes such as `[gallery]` and `[video]` where the theme uses them. Write a body even if templates never print it, because excerpts, search, and reading time use it; the exception is a post type that supports neither `editor` nor `excerpt`, where the text would be invisible and uneditable, so write none and report it if a template reads it anyway. Where a title or blurb names a number ("Eighteen frames", "five tips"), the item's own data must match that number. If the theme shows reading time or a reading-progress bar, vary body length so reading times spread (for example 1 to 6 minutes) and any length threshold the theme uses is crossed by some posts.
- **Other formats:** quote posts use a `<blockquote>` with a real citation; link posts store the URL where the template reads it; status, aside, and chat posts get short bodies in the shape their templates render.
- **Terms:** only where the theme registers them and something it renders shows them (archives, widgets, card meta): 10–15 categories and 40–60 tags, with 2–5 tags per post, so category and tag widgets have real counts. For each custom taxonomy, 4–8 terms, with 1–3 assigned to every post of the post types it's registered for (1 if the templates only show the first term). Give the two or three busiest terms more posts than `posts_per_page`, so a term archive paginates. Hidden taxonomies that only mirror a meta field or hold values the theme computes are filled by the theme, not the importer.
- **Authors:** about 6 users with the `author` role, only if the theme shows author names, author boxes, or author archives, in templates or in its structured data, with bios if the theme shows bios (if the bio box hides when the bio is empty, leave one author without a bio so both states show). Otherwise all posts belong to the admin user.
- **Dates:** spread to suit the theme's date views: several years if its templates link to or list year archives, ledgers, or "by year" lists, otherwise about the last 120 days. Put about a third in the last 7 days so "trending" and recent views have data. If the theme has a "today", "last hour" or "last 24 hours" view, put several posts in the last few hours before the anchor (see `seed`). Those views count back from the moment the page is viewed, not from the anchor, so they empty as the day goes on and `reset` fills them again; note that in the report rather than treating it as a bug.
- **Comments:** threaded, 0–12 per post, about a third of them replies, only on post types whose templates display comments. If a Customizer or options switch controls comments, turn it on and create them; if the theme hides or disables comments with no such switch, create none. Every comment is dated after its post and never in the future. Core closes comments on a new page by default, so open them on the demo pages whose template shows comments. If the theme itself forces comment pagination on, give one post enough comments to reach a second page; if pagination depends on core's `page_comments` option, leave it.
- **Counters:** any the theme reads, such as votes, views, or ratings, with a realistic skew.
- Every post and comment sets its GMT date too.

### Media

- **Images:**
  - Sideload each image with `download_url()` and `media_handle_sideload()`, attached to the demo item that shows it, whatever its post type (an ad or sponsor post type counts). Only site-level images that belong to no item (logo, site icon, images stored in settings) stay unattached but flagged.
  - Use deterministic picsum URLs: `https://picsum.photos/seed/<unique-seed>/<w>/<h>.jpg`. Picsum maps many seeds to the same photo, so compare downloads by file hash and by picsum's photo ID (the `picsum-id` response header, readable through the `http_api_debug` hook), because the same photo at different sizes has a different hash; re-seed duplicates. No two images may be the same photo unless a pool reuses them on purpose. The photos are stock shots and won't match the hand-written copy; that is expected and isn't worth working around.
  - Name each uploaded file `<seed>.jpg` so WordPress's file type check passes. Set the title, caption (`post_excerpt`), `menu_order`, and the parent post's `post_date` and `post_date_gmt` (otherwise attachments are dated now, after the anchor) in the `$post_data` argument, and the alt text in `_wp_attachment_image_alt`.
  - Create each image at the aspect ratio of the slot it fills, at about twice the displayed size, and never smaller in either dimension than the largest registered `add_image_size()` crop that slot feeds: WordPress never upsizes, so a source that is too small silently gets a wrongly proportioned crop, or none at all. After the first import, dump `wp_get_attachment_metadata()` for one image of each kind and confirm the sizes that kind's own slots use are there at their declared dimensions. A theme with both landscape and portrait hard crops can't have every registered size on every image; only the ones each slot shows matter. If one image fills slots of different ratios (a featured image in 4:3 cards and a 16:10 preview), use the ratio of the slot visitors see most, usually the card grid. Mix landscape, portrait, and square only where a slot shows the image uncropped; never put portrait or square images in a fixed landscape slot.
  - Reuse a shared pool where images don't need to be unique (for example gallery panels or screenshots), so a full run downloads about 100 images or fewer. If any code the page runs reads a post's child attachments (a gallery template, a zip builder, the theme's own structured data), sideload a separate attached copy per post from the cached download instead of sharing one attachment ID, and check that the featured image doesn't end up in those children too (attach it elsewhere, or use explicit IDs where the template accepts them). If the theme reads a post's attached images with no way to exclude the featured image, keep the attachment where it belongs and report the theme bug instead of misattaching the image.
- **Galleries** (only if the theme renders galleries): give each gallery the number of images its layout is built for: fill whole rows of the grid (for example 3 or 6 in a 3-column grid), respect any limit the template applies, and vary the count between posts within that. For a grid that fits as many columns as there is room for (CSS `auto-fit` or `auto-fill`), fill whole rows at the desktop width. Use 4–8 only when the layout sets no count at all. If the template has an overflow state (a "+N more" tile past a limit), give one or two galleries more images than the limit so it shows. Use whatever mechanism the templates read, and set a featured image if the feed cards use one.
- **Video and audio** (only the ones the theme plays):
  - Use real, freely licensed sources: for video, Blender open movies on YouTube, `download.blender.org`, `media.w3.org`, MDN's CC0 videos, or test-videos.co.uk; for audio, Wikimedia Commons or archive.org public-domain recordings. Store them in whatever form the template reads: an embed, `[video]` or `[audio]`, a meta URL, or attachments that a `[playlist]` or album template reads. A direct file URL must end in an extension WordPress's player accepts (audio: mp3, ogg, m4a, wav, flac; video: mp4, webm, ogv) with no query string, or the player silently becomes a plain link, so strip tracking parameters that APIs add.
  - Mix embed and direct-file sources if the theme supports both. Link direct files by URL and don't sideload them, unless a template needs an attachment ID (next sentence). If a template needs an attachment ID, sideload a pool of 3–5 small files (check each file's byte size before the first sideload, not just its status code, and keep each under 10 MB) once, cache them like images, and reuse their IDs on every post that needs one, so no picker stays empty. Hand pooled files out in round-robin order, so every file in the pool is used even at a small `count=N`, with one sub-pool per kind where the kinds need different files (short clips for a shorts layout, longer ones for full videos); a pooled attachment's parent is the first post that uses it. If a template reads a post's child attachments instead (an audio album or playlist), an attachment can have only one parent: sideload a separate attached copy per post from the cached download, as for galleries, ordered by `menu_order`. Core's playlist shows each attachment's caption in place of its title, so put credits in the description, not the caption.
  - Where a template shows a media duration, store the file's real length (for a sideloaded file, WordPress has already put `length` and `length_formatted` in its attachment metadata; read those rather than parsing the file again, and use `wp_read_audio_metadata()` or `wp_read_video_metadata()` only on a file you have on disk but haven't sideloaded), and leave a few empty only if the theme has an empty state for it. Audio posts get cover art (a featured image) where the templates show one.
  - Give each video post a poster or featured image, whichever the templates display. Never show the same photo twice on one page: if the single template shows both the featured image and the video's poster, give the poster a different image, or leave it unset when the player already uses the featured image.
- **Animated GIFs** (rare; skip unless a template shows them): if a template shows GIFs (a GIF slot, animated hover previews, a field that accepts only `.gif`), generate them locally instead of downloading, because photo sources serve only JPEG.
  - **Frames:** draw 6–12 frames with GD (a simple motion such as a moving shape or a colour sweep), about 100 ms apart.
  - **Assembly:** GD's `imagegif()` writes one frame at a time, each with its palette in a global colour table. So write one `GIF89a` header, a `NETSCAPE2.0` extension with loop count 0 (loop forever), then for each frame a Graphic Control Extension (delay 10 in hundredths of a second) and its image block, with that frame's colour table moved into a local colour table; otherwise every frame uses the first frame's colours.
  - **ffmpeg:** if `ffmpeg` is on the machine and you already sideloaded or cached a video clip for another reason, you may turn 2–3 seconds of it into a GIF instead; never download a clip just for this.
  - **Size:** make each GIF at least the size of the slot's crop and at most 2560 px on its longest side. WordPress's resized copies of a GIF keep only the first frame, which is usually what a hover preview wants (a still card that swaps to the animated original); a GIF smaller than the crop gets no resized copy, so it animates without hover, and one over 2560 px is replaced by a still `-scaled` copy. Keep each GIF under 1 MB.
  - **Upload:** sideload it like any image, but named `<seed>.gif` with type `image/gif`. Put GIFs on only some of the items that can take one, so the non-GIF state (a plain image, or the theme's own fallback) shows too.
- **Other files:** if a field needs a non-media attachment (a zip, PDF, or download file; audio and video follow the rules above), generate a small file locally (for example with `ZipArchive`) and add it to the media library; don't download one.

### Fields

Fill every meta field on every demo post, page, term, or user it applies to, and make sure `purge` removes every field you write, following the theme's own conditions (a "paid items only" field stays empty on free items). Put a meta field only where a template reads it (Customizer settings and theme options are all filled, as *Customizer and theme options* below says, even ones no template reads, except the code and secret fields listed under Code and secrets; report settings no template reads as theme bugs); fields the theme's own save handler adds by itself when you call it are the theme's behaviour, so leave them and mention any odd ones in `demo/BUGS.md`.

- **Valid values:** real options for selects and radios, the exact checked value for checkboxes, valid hex colours, correctly formatted dates, 2–5 rows for repeaters and groups, attachment IDs of images sideloaded for that post, and post IDs of other demo posts for relationships.
- **Only the stored part:** if the template prints "CSS | " before the value, store "38 KB", not "38 KB CSS".
- **URLs:** the invented brand, its products, and buy links use `example.com` placeholders or internal permalinks that match the field's meaning. Download links point at a generated file in the media library. Build internal links with `get_permalink()` and similar, so they work under plain and pretty permalinks. Never point at real third-party products or downloads; only media sources and social profile hosts are real.
- **Storage:** store each value exactly as the theme's save handler would. If the theme has its own save or sanitize functions or classes, call them with your values; otherwise match the save handler's sanitizing, serializing, and key prefixes. If the save handler's shape and what a template reads disagree, store the save handler's shape (the edit screen must keep working) and report the mismatch as a theme bug. For ACF, write with `update_field()` using field keys so the `_fieldname` reference rows exist. For CMB2, Meta Box, and Carbon Fields, match their storage format, such as group arrays or one row per value. If the save or sanitize function you need lives in a file the theme loads only in wp-admin (behind `is_admin()` or an admin hook), `require_once` that file first, because `wp eval-file` doesn't load it. If the handler reads `$_POST` and checks a nonce, call it with a temporary `$_POST` holding your values and a real nonce from `wp_create_nonce()` for its action, then restore the original `$_POST`. If a template reads a field that no meta box or save handler writes, store it in the shape the template reads and report the missing editor as a theme bug.
- **Every state:**
  - Cover the full range of every scored or enumerated field, including the extremes (for a 0–10 score, some posts below 4 and some above 9), so every styling threshold appears.
  - Make linked fields follow the value that drives them: labels, verdict text, badges, and feature checkboxes match the score or tier instead of staying the same on every post.
  - Leave optional fields that have an empty or fallback state (badges, ranks, sponsored flags, optional images or colours) unset on most items and set them on about 1 in 4 to 1 in 6, so both states show. This is for fields that are genuinely occasional. Fields that belong on almost every item of their kind (a video's duration, a download theme's download link) go on most items, with only a few left empty to show the empty state. When both rules could apply to one field, let the theme decide: a field the theme ships a fallback for, and its own editor leaves empty by default, is occasional; a field the templates print on every item of that kind goes on most. Sticky posts stay at 1–3, so they don't flood the first page.
  - Tailor repeated sub-content (features, pros and cons, personas) to each category; never reuse one product's list across unrelated categories.

### Site

- Permanently delete (not trash) core's default content at the start of an import if it is still there and unchanged (the "Hello world!" post, "Sample Page", and the default comment; unchanged means the default title and slug and a `post_modified` equal to its `post_date` for the post and page, and the default author name, email, and text for the comment), because it would outrank the demo content. `purge` doesn't recreate it.
- Content the theme seeds on activation is part of the empty site.
  - **Seeding status:** decide whether seeding ran by checking that the seeded items themselves exist, not a flag option (themes often delete their "seeded" flag on the first admin page load). If any seeded piece is missing, call the theme's own seeder, after reading it to confirm it only creates what's missing. Call it before switching to an admin user, the way `wp theme activate` runs it, because hooks that fire for a logged-in user can change what gets stored.
  - **Reuse:** reuse every seeded item and fill its empty fields like demo items, applying the occasional-field rule to them too. Seeded items count toward the term and page numbers in this file; if the seed already exceeds them, create no more of that kind.
  - **Widgets:** leave widgets the theme adds in place; they already show off its widgets.
- Assign nav menus to empty locations that a template actually displays, filling any per-item fields the theme adds (icons and the like) through its own handler, which needs the item to exist first: create the menu item, then fire the theme's hook for that item's ID with the values in both `$_POST` and `$_REQUEST` and a real nonce, since the handler's `check_admin_referer()` would otherwise stop the run; a location no template displays gets no menu and is reported as a theme bug. Add widgets to empty sidebars. A fresh install fills the first sidebars with core's default block widgets: if they are untouched, move them to Inactive and let `purge` restore them. If a sidebar's template shows useful fallback content only while it is empty (a menu, category counts), leave that sidebar empty. If any part of the fallback is placeholder or default text (for example "Set a form action URL"), it isn't useful; fill that sidebar with widgets and brand copy. If the theme fills its sidebars on activation, none may be empty; say so in the report.
- Create a page for each of the theme's page templates, plus a small standard set (About, Contact, Privacy) when menus, the footer, or settings link to pages, so those links stay internal. Use the exact slugs templates expect (for example `contact`). Core's draft Privacy Policy page already holds `privacy-policy`; leave that draft alone and give the demo page a different slug, so the flag rule still covers only what the importer created. If no template in the theme renders a page's own content, create no pages and report it: the pages would only add broken URLs.
- Set the homepage settings the templates rely on, for example `show_on_front=posts` when the home page is the post listing.

### Customizer and theme options

Fill every Customizer setting and every theme options field with one consistent fake business or site profile: the `BRAND` input, or one you invent that fits the theme's niche.

- **Identity:** always set the site name, tagline, and site icon, even if the theme never reads them, because core shows them in the browser tab, feeds, and page head. The logo is the one identity setting that can be better left unset (see below); the site icon is always set. Set a logo only if the theme supports `custom-logo`; if it declares support but no template displays the logo, set it anyway and report that as a theme bug. Before setting one, read what the header prints when no logo is set: if it prints a designed wordmark (the site name with its own classes, font, colour or decoration, such as a styled `<span>` or an animated dot) rather than plain text, leave the logo unset so that design shows, and let the brand name appear through the site name; say so in the report. Draw a logo only when the no-logo fallback is plain text. Draw the logo and site icon with GD, not from a photo: the logo as the brand name in a bold font on a solid colour from the theme's palette, sized at twice the `custom-logo` dimensions (same ratio) or about 240×60 when the theme declares none (for a square slot, use a short mark such as the brand's initials instead of the full name); the icon as the brand's first letter, at least 512×512. Save both as PNG in the media library.
- **Brand details:** contact email (`@example.com` only), phone (`555-01xx` numbers), an obviously fictional street address, opening hours, copyright or footer text, social profile URLs (for example `https://x.com/<brand>`), CTA button text and links, announcement bar text, and an about blurb. Put details the theme has no field for (phone, address, hours) in the Contact page body, so they still appear somewhere; if the theme renders no pages, say so in the report instead.
- **Copy:** fresh, realistic copy that fits each field's label and where it appears, for every text setting and field, generic UI labels included ("Search", "Date", "Clear this tag"); never leave the theme's default wording. Labels stay short and do the same job as the default. WYSIWYG fields get simple HTML (paragraphs, bold, links), and text repeaters 2–5 rows. Keep the copy in one brand-profile array plus per-section arrays so a large panel stays readable.
- **Valid values:** a real choice for selects and radios; every site-wide switch that shows or enables something (sections, notices, badges, downloads, comments) set to on, so its output shows even when it fits the brand poorly; if one of them puts an overlay in front of the whole site (an age gate, a cookie wall), say in the report how to get past it; hex colours that fit the theme's palette; range values inside the control's bounds; page dropdowns pointing at demo pages; a sideloaded picsum image for header images, stored as a URL or ID to match the setting.
- **Code and secrets:** never write to settings or fields meant for raw code or secrets, such as core's `custom_css[<stylesheet>]`, custom CSS or JS, header or footer scripts, analytics IDs or tracking snippets, API keys, and license keys. Keep their current values, and list their names (never their values) in the report. The one exception is an embed field on a demo item the importer itself creates, whose purpose is to show that embed on that item (for example an iframe ad post): give it a harmless `https://example.com/` iframe. If the theme's options sanitizer rewrites a whole array and stores untouched code keys as empty strings, that is acceptable only when they were already empty; `purge` still restores the exact original array.
- **Customizer route:** Customizer settings aren't registered under `wp eval-file`, so load `wp-includes/class-wp-customize-manager.php`, create `$GLOBALS['wp_customize'] = new WP_Customize_Manager()`, and fire `do_action( 'customize_register', $GLOBALS['wp_customize'] )`. Then write each value with `$wp_customize->set_post_value( $id, $value )` followed by `$wp_customize->get_setting( $id )->save()`. That runs the setting's own validate and sanitize callbacks and stores the value correctly whether it is a theme mod, an option, an array ID like `<theme>_options[footer_text]` (merged into the existing array), or a framework-specific type; the header image goes the same way, which also writes `header_image_data`. After the last `save()`, fire `do_action( 'customize_save_after', $GLOBALS['wp_customize'] )` once, because themes often build derived values on that hook. If `get_setting( $id )` returns null (a mod the templates read that has no registered setting), write it with `set_theme_mod()` if it is a theme mod (never for core options such as `blogname`) and note that in the report. A theme that registers no Customizer settings at all still has core's identity settings (`blogname`, `blogdescription`, `site_icon`, `custom_logo`): write those the same way, and use them for the step 1 markers.
- **Theme options route:** write through the theme's own storage format. If the theme keeps everything in one array, merge your keys into the existing array instead of replacing it. For ACF options use `update_field( $key, $value, 'option' )`. For Redux and similar frameworks, update the framework's option array and keep any keys you don't set.
