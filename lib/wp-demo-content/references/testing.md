# Step 4 - test it for real before reporting back

Always test in a throwaway WordPress, even when a real site is reachable. The harness
itself is `setup-test-site.md` in this folder; copy it by line range and check its hash
before running it.

Always test in a throwaway WordPress, even if a WordPress site is reachable from here. Never run the importer, `reset`, `purge`, the marker writes below, or any other `wp` write command against the site this theme is installed in, and never read or reuse that site's `wp-config.php` or database credentials.

**Setup.** Put the script from `${CLAUDE_PLUGIN_ROOT}/lib/wp-demo-content/references/setup-test-site.md` (lines 18-579 of that file), unchanged, in a new file outside the theme - `script=$(mktemp --suffix=.sh)`, then `sed -n '18,579p' <that file> > "$script"`. Copy it by line range; never retype it. Check that `sha256sum "$script"` prints `dcf0a8158e53ad0b8d526dc7c15b61e50e38d0926a33914e41a13ebbfd30b1a2` (if it doesn't, the copy differs from the reference file: write the file again in one go, and never edit it to make the hash pass), run it from outside the theme directory with the theme directory and port 8080, and keep the folder it prints on its last line as `<tmp>`. If 8080 is in use, run it again with port `0` (the bare number), which picks a free port; never stop a process you didn't start. Always build URLs from `$WP_TEST_URL` (set in `<tmp>/env.sh`), never from a literal port:

```
bash "$script" <theme-dir> 8080
source <tmp>/env.sh
```

The script needs Linux with bash 4.4 or newer; it checks for `curl`, `php`, `unzip`, `mktemp`, `timeout`, and PHP's `pdo_sqlite` extension, refuses a port that is already in use (port `0` picks a free one), and removes its temp folder if any step fails (set `KEEP_ON_FAILURE=1` to keep it for inspection). It creates a new temp folder, downloads WP-CLI (the nightly build on PHP 8.5 or newer, or whenever the stable one prints `Deprecated` lines), installs WordPress on SQLite with WP-Cron off and `WP_DEBUG`, `WP_DEBUG_LOG`, and `WP_DEBUG_DISPLAY` on (PHP errors print in the page and are logged to `<tmp>/wordpress/wp-content/debug.log`), sets pretty permalinks, confirms `siteurl` equals the chosen URL, installs and activates the Classic Editor plugin (as on the real sites), and symlinks and activates the theme. The site keeps WordPress's default content and reports `production`. After `source <tmp>/env.sh`, these commands are on the path. Tool shells often don't keep state between commands, so either source `env.sh` in every command or call each helper by its full path, `<tmp>/bin/<name>`, which works without sourcing:

- `wp …`: WP-CLI pinned to the test site, running from its WordPress root (pass file arguments as absolute paths), with its cache, packages, and config inside `<tmp>`. `TMPDIR` also points inside `<tmp>`.
- `serve start` / `serve stop` / `serve status`: the `php -S` server in the background (512 MB memory limit), logging to `<tmp>/server.log`.
- `login`: logs in as admin (`admin` / `admin`) and saves the cookie jar at `<tmp>/jar` for `curl -b <tmp>/jar`.
- `shot <url> <file.png> [width] [height]`: a headless Chrome screenshot, 1440×2400 by default. It sets the viewport through Chrome's DevTools protocol (Node.js 22 or newer), so 390 really lays the page out at 390px, and runs under a 1.5 GB memory cap (where systemd allows it; otherwise it warns and runs uncapped) and a 90-second timeout. Set `SHOT_INIT_JS` to JavaScript that runs before the page's own scripts, for example to set a cookie or `localStorage` flag. It needs Chrome or Chromium and Node.js 22 or newer; if either is missing it prints why and exits with code 3, and the setup script warns about it at the end.
- `teardown`: stops the server and deletes `<tmp>`.

If the script fails, fix the cause only if it's in your environment (for example a missing PHP extension); otherwise mark testing BLOCKED with the script's error. Don't edit the script. Then install and activate every plugin the theme depends on (from its TGMPA list or plugin checks); if one can't be installed, mark its import path BLOCKED.

**Rules for every step.**
- Queries run on SQLite, not MySQL; say so in the report. Inspect data with `wp eval` only, because `wp db` commands expect MySQL.
- Never print whole pages or logs into the conversation. Save each curl response to a file and grep it for the expected markup and for PHP error lines (`Warning:`, `Notice:`, `Deprecated:`, or `Fatal error:` followed by `on line`); a bare word like `notice` gives false matches from admin CSS classes. Ignore lines from WP-CLI's own files. Run phpcs with `--report=summary` first, then show only the lines you need.
- If a step can't run (no network, a missing tool), mark it BLOCKED with the reason. Never report a step as passed unless you ran it. Don't spend more than about 3 attempts or 15 minutes on one failing step; mark it BLOCKED with what you tried and move on.
- After the first full import, check the size of `wp-content/uploads` (for example with `du -sh`). Hundreds of megabytes means something downloaded is far larger than it should be.
- Never use `pkill -f`, which can kill your own shell.
- Take screenshots only with `shot`, one at a time. Don't use Playwright or browser automation tools: a runaway headless browser can use several GB and take the whole machine down.

**Steps.**
1. Before any import, set 2–3 Customizer settings, and one theme options field if the theme has an options panel, to marker values, such as a site title of `ORIGINAL-TITLE`. Later steps check these come back. Write the options marker directly (for example `update_option()` with just that key in the array), not through a theme sanitizer that rebuilds the whole array, so no other option changes.
2. Check every video and audio URL. Check each one once, with a small range request and a descriptive `User-Agent`, a second or more apart; never probe media hosts in bulk (for example with ffprobe), because Wikimedia and similar hosts answer with 429 for a long time. Direct files must return 200 or 206, and their size (`Content-Length`, or `Content-Range` on a range request) must be under 10 MB: `media.w3.org/2010/05/bunny/movie.mp4` answers 206 and is 249 MB. Reject anything larger and find a smaller clip. Check YouTube and Vimeo through their oEmbed endpoints (`https://www.youtube.com/oembed?url=…`, `https://vimeo.com/api/oembed.json?url=…`), because a removed YouTube video still returns 200. Some well-known sample buckets now return 403, so never assume a URL works. If a host throttles, confirm the file through its API and mark the check partly BLOCKED. Replace dead URLs now. `example.com` placeholders and social profile URLs are exempt. If the theme uses no video, audio, or embed URLs, say so and skip this step.
3. Run phpcs on the importer (install WPCS through Composer in a temporary directory of its own, not inside `<tmp>`, because `teardown` deletes `<tmp>`). Use the theme's `phpcs.xml` or `phpcs.xml.dist` if it has one; otherwise use the WordPress standard minus the rules the theme's own code breaks in most of its PHP files (for example short array syntax, `@param` tags, or `@var` on properties), each one evidenced by a count from the theme's own files, and list the excluded rules in the report. You may also exclude a rule that only fires because of an exclusion you already made; list those too. `--exclude` only takes whole sniffs; to drop a single message code, write a small ruleset XML in that same directory. If the theme's own ruleset conflicts with its own code style, the ruleset wins for the importer; put any extra exclusions in a wrapper ruleset that references the theme's file, and list them. The importer must end with zero violations, errors and warnings alike; a warning on a rule the theme's own code never triggers is a reason to change the importer, not to exclude the rule.
    **Ignores.** Things this procedure requires (seeded `mt_rand()`, `$GLOBALS['wp_customize']`, direct database updates such as the `post_modified` fix-up in Order, the meta queries that find flagged items for `reset` and `purge`, the temporary `$_POST` a theme's own save handler needs (building it as one array literal avoids most of those sniffs), `WP_IMPORTING` and core's own hook names failing the prefix sniffs, the `meta_key` slow-query sniff the flag lookups raise, `unlink()`, `file_get_contents()` and `file_put_contents()` under `WordPress.WP.AlternativeFunctions`, GD calls that PHP 8.5 deprecates, and the fixed file name `demo-import.php` holding a class) get a `phpcs:ignore` comment naming the rule and the reason. The file-name sniff reports on line 1, so put its ignore on the opening tag: `<?php // phpcs:ignore WordPress.Files.FileName.InvalidClassFileName -- <reason>`.
4. Run a small import (`count=N`, with N large enough for one post of each format and post type) and inspect the result with `wp eval`: formats, meta, featured images, attachment parents and order, terms, and comments.
5. While the small import's demo content is still there, run the importer again with no arguments and confirm it refuses. These runs happen on a site reporting `production`, which proves the importer works there.
6. Run `purge` and confirm that zero demo posts, attachments, users, terms, and uploaded files remain, and that the marker values from step 1 are back.
7. Run the full import and time it, then run `verify` and confirm it reports nothing. Don't run more full imports than the steps call for; reruns required by step 12 don't count.
8. Run `reset seed=1` twice. Record post dates as day offsets from that run's own anchor, plus whichever of counter values and comment counts the theme has, after each run, and confirm they're identical. Check the UTC clock before you start: the offsets hold across midnight, but any absolute date you also record won't. Compare records by post slug, not ID, because IDs change on every reset. Confirm the demo post count (published demo items of type `post` and the counted custom post types, excluding pages, attachments, and menu items) equals the target, with no leftovers from the earlier run.
9. Run `serve start`, and `login` for wp-admin pages. Fetch the home page, every sort or filter mode the theme has, a category archive if it has one, and at least one single page per format and post type; name the ones the theme doesn't have. Confirm each returns 200, contains the markup the theme's templates actually output for each feature (gallery viewer, embed iframe, `<video>` or `<audio>`, a `wp-playlist` block with its track JSON, figure, comments where shown), and has no PHP warnings or notices in the HTML, `<tmp>/server.log`, or `<tmp>/wordpress/wp-content/debug.log`.
10. For meta fields, Customizer settings, and theme options: (a) confirm with `wp eval` that each listed item holds a valid demo value in its stored format and that code fields are unchanged; (b) while logged in, load one edit screen per post type and page template, `customize.php` (its settings data holds each demo value; current WordPress prints each value on its own line; grep for `s["<id>"] = `), and each options page, and confirm there are no notices and the values show; (c) find each value on the front end, including the brand's logo, contact details, social links, and colours.
11. **Screenshots.**
    - **When:** if `shot` exits with code 3, it is unavailable on this machine: take no screenshots, mark this step SKIPPED with the reason it printed, and carry on with the other steps. If you already know the importer will change again, leave the whole step until after the step 12 rerun, so the shots show the final data and step 12 has none to retake.
    - **What:** the home page, one archive, and one single page per content kind and post type; for a post type with no single view, the archive or page where its items appear, including a type that only ever appears inside other content.
    - **Sizes:** each page at 1440 wide and 390 wide (phone). If the content starts below a stacked sidebar, pass a taller height so it is in the capture. For a page shorter than the viewport, pass a height close to the page's own height: an over-tall viewport can repeat content in the capture, and `shot` can't tell you the page height, so take one, look at it, and retake it shorter if the content repeats.
    - **Names:** save them in the theme's `demo/screenshots/` as `<page>-desktop.png` and `<page>-mobile.png`, where `<page>` names the template as well as the kind when one kind has two layouts (`single-gallery-grid`, `single-gallery-slider`).
    - **Overlays:** if an age gate, cookie banner, or other overlay covers the pages, take one screenshot pair with it showing, then bypass it for the rest by setting the cookie or storage flag it checks with `SHOT_INIT_JS` (for example `SHOT_INIT_JS="localStorage.setItem('age_ok','1')" shot …`) or a URL parameter the theme honours, without changing the theme or the script. If the overlay is decided on the server, `SHOT_INIT_JS` runs too late to stop it being rendered: set the cookie it checks and reload once, guarding the reload with a flag in `sessionStorage` so it can't loop. If neither works, take every screenshot with the overlay showing and say so.
    - **Measuring:** when a section looks empty or something seems to cover the page, measure it rather than guessing: `SHOT_INIT_JS` can log `getBoundingClientRect()` or `document.elementFromPoint()` for the element in question. Content that fades in on scroll may still be loading in a capture; say so rather than treating it as a bug.
    - **Review:** if you can't view images, don't guess: say so, mark the visual review SKIPPED, and still save the screenshots. Otherwise look at every screenshot and report visual problems: badly cropped images, text overflowing its box, overlapping elements, sections that look empty or broken. Fix the ones the demo data causes and retake those shots; report the ones the theme causes as theme bugs.
12. **Reruns.** If you changed the importer after step 4 for any reason (phpcs fixes, replaced URLs, bug fixes, screenshot fixes), rerun on the final file now, before the last purge. Note the file's hash when each step runs, and rerun only the steps that ran on an older file: `purge`, then step 1 if its markers are gone, then steps 3, 4, 5 and 6, a timed full import followed by `verify`, and step 8. Report that timed import as the final timing. If step 11 already ran, retake only the screenshots whose pages changed; if you deferred it, run it now. Results from an earlier version don't count.
13. Run `purge` last. Confirm the marker values from step 1 are restored exactly, every setting that didn't exist before is gone, the logo shown matches the pre-import state, the backup option is deleted, and menu locations and sidebars match their pre-import state. Ignore the exempt values in `${CLAUDE_PLUGIN_ROOT}/lib/wp-demo-content/references/importer-spec.md`, items WordPress core creates on its own (such as a `wp_global_styles` post, a `wp_theme` term, or cron events core schedules after an admin page loads), and options the theme itself creates when a page loads (for example a rewrite or migration version set on `init` or `admin_init`); name the latter in the report.
14. Run `teardown`. Keep the WPCS folder if the bug-fixing step might need phpcs again; delete it (if it's outside `<tmp>`) once bug fixing is finished or the developer declines fixes.
